# 標的池調整：美股限定、500 檔、排除中概股

> 對應需求：
> 1. 篩選範圍限制為美股，只納入在美國交易所上市的個股，標的池擴大至 500 檔。
> 2. 明確排除所有中概股，設為篩選流程的固定規則，選股／回測／分析皆須遵守，
>    並在輸出結果標註已排除中概股與因而調整的標的數量。

## 2. 500 檔是怎麼來的（可稽核）

母體採用 **S&P 500 成分股**。選它的理由不只是「剛好 500 檔」，而是它的定義
同時滿足需求的三個硬條件：

| 需求 | S&P 500 為何滿足 |
|---|---|
| 只納入美國交易所上市個股 | 成分股全部在 NYSE / NASDAQ 掛牌 |
| 排除中概股 | 指數要求**美國註冊**；中概股多為開曼註冊的 ADR，結構上進不來 |
| 恰好 500 檔 | 指數規模即 500 家 |

⚠️ 一個容易搞錯的細節：Wikipedia 的成分股表有 **503 個代碼**，但那是
503 個*代碼*，不是 503 家公司。其中 3 組是同一家公司的第二類股：

| 保留 | 排除 | 原因 |
|---|---|---|
| `GOOGL` | `GOOG` | Alphabet A 股 / C 股 |
| `FOXA` | `FOX` | Fox A 股 / B 股 |
| `NWSA` | `NWS` | News Corp A 股 / B 股 |

去除這 3 個重複**公司**後，剛好 **500 家**。留 A 股而非 B/C 股，因為
技術分析要的是流動性；B/C 股成交稀薄時，ATR、均量、支撐壓力都不具代表性。

這條規則是明寫在 `scripts/build-pool.js` 的 `DUAL_CLASS_DROP` 表裡，
不是用「名稱去掉 (Class X) 後相同就合併」的自動規則 —— 自動規則在名稱
寫法不一致時會漏判（例如 `BRK.B` 的名稱根本沒寫 Class），而「不得重複」
是本次需求的硬條件，漏判必須看得見。

## 3. 中概股排除：為什麼命中數是 0，但規則仍然存在

這是本次最需要說清楚的一點，否則會被誤認為「規則沒生效」。

**S&P 500 母體目前一檔中概股都沒有**，命中數是 **0**。原因是結構性的：
指數要求美國註冊，中概股幾乎都是開曼註冊的 ADR。

那為什麼還是把排除做成硬規則：

1. **母體換掉時閘門必須已經在。** 若哪天改成「美股全體」，這道閘門
   就立刻有用；等換了才補是來不及的。
2. **母體不是唯一入口。** 篩選器可以被呼叫方直接餵 `symbols`
   （測試、外部 cron、未來的新 API、排程器）。閘門放在**篩選器內部**
   才是「固定規則」，放在母體只是「預設值」。
3. **需求要求標註數量。** 即使是 0 也必須講，否則使用者無法分辨
   「規則跑了但沒命中」與「規則根本沒啟用」。

### 規則落在哪一層

```
請求 → pool.byMarket()          ← 母體（已 500 檔純美股）
     → screener.screen()
         → pool.enforceUniverse(symbols)   ← ★ 唯一閘門（中概股 + 非美股）
             → analyzer.analyze(每檔)      ← 被排除者不產生任何上游請求
```

閘門放在 `analyze()` **之前**，所以被排除的標的連 3 個上游請求都不會發。
這不只是省資源：若留到 `applyFilters` 才排除，排除原因會顯示成
「市場不符」或「評分不足」，使用者會以為放寬條件就能看到，事實上是
永遠不會出現 —— 理由必須誠實。

### 雙重比對：代碼 + 名稱

| 方式 | 作用 | 失效模式 |
|---|---|---|
| 代碼黑名單（`CHINA_ADR`，68 檔） | 熱路徑零成本 | 漏掉新上市的中概股 |
| 名稱詞邊界比對（`CHINA_NAME_RE`） | 補漏 | 需要名稱資料 |

名稱比對**必須用詞邊界**（`\b`）。這不是理論問題，實測踩過：
寬鬆的 `/nio/` 會命中 `Dom`**`inio`**`n Energy`、`U`**`nio`**`n Pacific`；
`/cn/` 會掃到 `Old Dominion`。誤傷的代價是把正常美股踢出母體，
而使用者看到的理由是「已排除中概股」，完全無從理解。

### 4.2.1 `MAX_HOLDINGS`：母體擴大後才浮現的舊上限

把母體從 154 擴到 500 之後，版塊輪動流程的漏斗出現一個無法解釋的缺口：
**500 檔裡只有 405 檔查得到版塊歸屬**，其餘 95 檔被標成「無歸屬」。

根因不在版塊資料，而在 `MAX_HOLDINGS`：

```js
// lib/sector-holdings.js（修正前）
const MAX_HOLDINGS = 50;
```

這個上限原本是為「持股表只顯示前 N 大」而設，但 `getSectorIndex()` 拿同一份
持股去建「個股 → 版塊」對照表，於是 **50 變成了覆蓋率天花板**。各 SPDR 產業
ETF 的實際持股數是 XLI 83、XLK 76、XLF 76、XLV 60…… 排在第 51 名之後的
成分股，在對照表裡就是「查無版塊」。

它為什麼危險：**症狀偽裝成資料限制**。呼叫端無法區分

- 「這檔股票不屬於任何版塊」，與
- 「它屬於某版塊，但排在該 ETF 持股第 51 名之後」

兩者在下游長得一模一樣。被誤判的 95 檔包含 CTSH（XLK 第 54 名）、
AKAM（XLK 第 52 名）這類正常大型股 —— 不是邊緣小型股。若不修，
版塊輪動流程會無聲丟掉 **19% 的母體**，而且漏斗上的數字仍自洽
（405 + 95 = 500），不會有任何錯誤訊息。

修正與取捨：

| 上限 | 有版塊歸屬 | 覆蓋率 | 誤判無歸屬 |
|---|---|---|---|
| 50（舊） | 405 / 500 | 81% | **95 檔** |
| 300（新） | **500 / 500** | **100%** | **0 檔** |

為什麼是 300 而不是 `Infinity`：持股檔是外部資料，筆數不該無上限地吃記憶體
與 CPU。實測最大的 XLI 也只有 83 檔，300 已足以涵蓋任何現實中的 SPDR 產業
ETF，同時仍是明確的護欄。

驗證方式：版塊輪動流程的漏斗與覆蓋率行現在應顯示「0 檔未歸屬」；
若非 0，畫面會亮紅字提示**檢查持股檔**，而不是提示放寬篩選條件 ——
因為前者才是真正的原因。

這個上限原本沒有任何測試釘住，正是它能悄悄退化的原因。現在補了三條：

| 斷言 | 防的是什麼 |
|---|---|
| `E4` `MAX_HOLDINGS >= 100` | 有人「順手」把它調回 50 之類的小數字 |
| `E5` limit 夾制語意 | 呼叫端傳超大 `limit` 時仍受上限保護；`0` / 負數 / `undefined` 的退回值 |
| `E6` `getSectorIndex` 用 `limit: MAX_HOLDINGS` | 有人把它改回寫死數字 —— 這正是原本的 bug 形態 |

`E6` 讀原始碼做斷言，因為這個錯誤不會改變任何回傳值的**形狀**，
只會讓資料變少；行為測試很難察覺，原始碼斷言才擋得住。
兩處變異（上限改 50、`limit` 寫死 50）實測都會讓對應斷言失敗。

## 5. 效能影響（必讀）

`analyzer.analyze()` 每檔要打 **3 個上游請求**。

| 母體 | 請求數 | 併發 4 的預估耗時 |
|---|---|---|
| 154（舊） | 462 | 12–25 秒 |
| 500（新） | 1500 | 約 40–80 秒，視上游延遲 |

因此 **90 秒的預設預算在多數情況下跑不完全池**。這是預期行為，不是故障：

- 互動查詢（`/api/screen`）：達預算即停，回報 `timedOut: true`，
  且 `notes` 會寫「已達單輪時間上限，本輪僅檢查 N / 500 檔」。
- 每日清單（scheduler）：改用較寬預算（預設 4 分鐘），否則「每日候選池」
  會退化成「每日前段候選」。

要調整請設環境變數（Render Dashboard → Environment）：

| 變數 | 預設 | 說明 |
|---|---|---|
| `SCREEN_BUDGET_MS` | 90000 | 互動查詢的時間上限；背景批次取其與 4 分鐘的較大值 |
| `SCREEN_CONCURRENCY` | 4 | 併發數，上限 8。實測併發 8 開始出現零星 429 |

## 6. 已知限制

1. **中概股名單需人工維護。** 代碼黑名單涵蓋 68 檔常見 ADR，新上市的中概股
   需補進 `CHINA_ADR`（`lib/pool.js` 與 `scripts/build-pool.js` 各一份）。
   兩份若不一致，測試 A8 會失敗 —— 這是刻意的，避免「改了名單卻沒生效」。
   名稱比對可補漏，但依賴上游提供名稱。
2. **快照不會自動更新。** S&P 500 每季調整成分股，需重跑
   `node scripts/build-pool.js` 並提交 diff。這是刻意的：母體變動必須是
   一次看得見的 commit，而不是某天早上悄悄換掉。
3. **快照遺失時會降級。** 若部署漏帶 JSON，`lib/pool.js` 會退回
   `lib/alias.js` 推導的美股清單（約 84 檔），並在 `summary.degraded`
   與啟動日誌明確標示。不會靜默變成 0 檔。
4. **版塊歸屬依賴 ETF 持股檔。** 對照表由 11 檔 SPDR 產業 ETF 的持股建立
   （`lib/sector-holdings.js`），因此「個股屬於哪個版塊」是**依 ETF 成分**
   而非官方 GICS 分類。兩者多數一致，但邊界公司可能不同。
   若持股檔抓取失敗，該版塊的成員會全數落空 —— 此時覆蓋率行會亮紅字，
   提示檢查持股來源，而不是提示放寬篩選。持股上限見 §4.2.1。

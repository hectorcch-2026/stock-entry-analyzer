# K 線預測與 AI 選股 — 交付說明

對應規格：`docs/K線預測與AI選股規格書_v1.3.md`
實作範圍：三頁導航、K 線圖表互動、預測與可信度呈現、AI 選股、前後端串接
驗收狀態：10 個測試套件全綠（含既有 8 個回歸 + 新增 2 個）

---

## 一、本地啟動

```bash
cd stock-entry-analyzer
npm install                      # 若尚未安裝
npm start                        # 預設 http://localhost:5177
```

開發模式（改檔自動重啟）：

```bash
npm run dev
```

不需要資料庫、不需要環境變數即可跑起來。三個選用環境變數見第四節。

---

## 二、驗證方式

### 2.1 手動走一遍（約 3 分鐘）

| 步驟 | 操作 | 預期 |
|---|---|---|
| 1 | 開 `http://localhost:5177` | 顯示歡迎頁，上方有「K 線預測 / AI 選股」導航 |
| 2 | 輸入 `AAPL` 查詢 | 結果區出現評分、買區、預測卡片、可信度卡片 |
| 3 | 點圖表上方 `3m`／`2y`／`5y` | K 線根數改變，狀態列顯示「N 根日線 · 來源」 |
| 4 | 在圖表上滾輪上下、拖曳 | 縮放與平移；右上角顯示「第 A–B 根 · 共 N 根」 |
| 5 | 按 `⟲` 或雙擊圖表 | 回到全覽 |
| 6 | 切到「AI 選股」 | 表單已帶入預設值，標的上限顯示真實檔數（154） |
| 7 | 直接按「開始篩選」（不改任何欄位） | 約 2–5 秒出結果表，統計列顯示池/檢查/符合/耗時 |
| 8 | 點任一欄位標題 | 就地重排（不會重跑篩選） |
| 9 | 點任一列 | 跳到 `#/detail/代碼`，上方出現返回列與「代碼 個股詳情」 |
| 10 | 按「返回」 | 回到選股頁，**篩選結果與排序都還在** |
| 11 | 把「結果筆數上限」貼上 `99999` 再送出 | 顯示錯誤卡「篩選條件有誤」＋可用的恢復操作 |
| 12 | 瀏覽器開發者工具切到手機尺寸（390×844） | 無水平捲動，圖表工具列與表單仍可用 |

## 五、設計取捨（實作時的主要判斷）

### 5.1 信心度改為「統計可信度」

規格要求「趨勢判斷 + 信心度」。但路徑 A 已刪除方向機率，若把信心度做成
「上漲機率」等於把刪掉的東西換個名字放回來。改為三項加權：

- **校準 45%** — 回測 PICP 對 80% 目標的雙向偏離。**雙向**是關鍵：PICP 45%
  與 95% 得分相同，否則「把區間放到 100% 寬」就能刷高分。
- **樣本量 30%** — 用 walk-forward 原點數，不是總樣本數（重疊的 h 日報酬不獨立）。
- **資料品質 25%** — 復權狀態、異常根、停滯。

缺失成分時**重新加權**而非記 0 分，否則「沒跑回測」會被誤報成「校準極差」。

「趨勢判斷」改為幾何描述：區間重心偏上／大致對稱／偏下，並明確標注非方向。

### 5.2 詳情頁共用預測頁的 DOM

不另建一份 DOM，改用「返回列 + 自動查詢」的入口模式。原因：19 個測試鎖定的
選擇器若複製一份，任何一處改動都要同步兩份，回歸風險翻倍。

### 5.3 有界併發而非 `Promise.all`

`analyzer.analyze()` 每檔打 3 個上游請求，154 檔同時發就是 462 個請求，
必然 429。實測併發 4：港股 70 檔 3.4 秒、全池 154 檔約 7 秒。

### 5.4 惰性補跑取代純定時器

免費方案容器閒置 15 分鐘休眠，`setInterval` 不會觸發。改為每次造訪檢查
「今日收盤已過且今日清單不存在」就當場補跑，並用每日檔案鎖避免重複。
純定時器與外部 cron 作為可選層保留。

## 六、實作中修掉的缺陷

以下都是在瀏覽器實測時才暴露、單元測試抓不到的問題：

1. **篩選按鈕完全無反應（最嚴重）** — `#fMaxAtrPct` 的 `step="0.5"` 配
   `min="0.1"`、`#fLimit` 的 `step="5"` 配 `min="1"`，兩者的預設值
   （`12`、`30`）都不在合法格點上。HTML 原生校驗因此擋下提交，`submit`
   事件從不觸發 —— 使用者按下按鈕後畫面毫無反應，也不報錯。
   已修正 `step` 並加上 `formnovalidate` + 前端自檢，把攔截點移到自己
   的程式碼裡才能給出「哪一欄不對」。

2. **`#screenHint` 覆寫掉內層 span** — 用 `textContent` 更新文案會銷毀
   裡面的 `#poolCountHint`。改用 `innerHTML` 重建同一結構。

3. **詳情頁麵包屑永遠是「個股詳情」** — `#detailCrumb` 從未被賦值。
   已補上「代碼 個股詳情」，含 `?symbol=` 入口那條不經過 router 的路徑。

4. **FVG 負索引畫出假區間帶** — 縮放後 `fromIdx - absOffset` 可能為負，
   `drawFVG` 會把它夾成左邊界，畫出一條從左延伸到右的假帶子。已補
   `>= 0` 過濾。

5. **`isFinite(null) === true`** — `/api/kline` 的 `price` 因此在沒傳值時
   回 `null`。改用 `typeof x === 'number' && isFinite(x)`。

6. **`flatten()` 誤判全部失敗** — `analyzer.analyze()` 的成功結果**沒有**
   `ok` 欄位（`ok` 是 `server.js` 在送出路徑才補的）。檢查 `analysis.ok`
   會把 70 檔全部判成失敗。改為檢查 `meta` 與 `score`。

## 七、已知限制

- **上游長區間取數會退化** — yahoo 對 `10y` 的請求在進程長時間執行後可能
  開始回「查無此標的的行情資料」，導致預測卡片進入不可用狀態（此時分數
  顯示 `—` 而非 `0`，並如實說明原因）。重啟進程即恢復。這是上游行為，
  非本專案邏輯問題，但值得在長期部署時留意。
- **篩選耗時隨池大小線性成長** — 全池 154 檔約 4–8 秒，`requirePred=1`
  會再多一倍。免費方案的請求逾時上限需留意。
- **每日清單需有人造訪才會產生** — 這是惰性補跑的必然結果。若需要
  「無人造訪也準時產生」，請設 `ENABLE_INPROCESS_CRON=1` 並使用不休眠
  的方案，或接外部 cron 打 `?run=1`。

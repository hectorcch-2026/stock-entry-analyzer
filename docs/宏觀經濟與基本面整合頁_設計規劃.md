# 宏觀經濟與基本面整合頁 — 設計與功能規劃

> 版本 v1.0 ｜ 2026-11-26 ｜ **規劃文件，不含程式碼**
> 專案：`stock-entry-analyzer`（Node 內建 http/fs、原生 JS IIFE、Canvas，`dependencies: {}`）

> **實作結果與本規劃的差異（後續決策）**
>
> 本文 §1.1 建議把「新聞＋財報」塞進 `#/macro/:symbol`，讓宏觀頁兼任個股整合頁。
> 實作後發現這個折衷並不成立：財報的資料粒度是一家公司，宏觀的粒度是全市場，
> 前者一旦隨代碼切換，整個頁面（含 FOMC、資料限制、AI 解讀）都被換成單一公司的內容，
> 宏觀資料形同被覆蓋。因此最終改為**責任分離**：
>
> - `#/macro` — 純全市場宏觀儀表板，移除個股輸入框
> - `#/detail/:symbol` — 個股詳情頁，財報卡（`public/stock-fin.js`）與新聞 AI 卡並列
> - `#/macro/:symbol` 舊網址保留，進站即轉址到 `#/detail/:symbol`
>
> 本文其餘部分（資料源實測、欄位定義、快取策略、效能預算）仍然有效，可作為背景參考。
> 現行路由歸屬以《宏觀經濟與企業財報_數據字典與API規格.md》的勘誤表為準。

## 摘要：先講三件會影響決策的實測結果

在寫這份規劃前，我把三個外部資料源全部實打過一遍。有三個結論會直接改變設計，先講：

| # | 實測結果 | 對設計的影響 |
|---|---|---|
| 1 | **FRED 的 ISM 製造業指數（`NAPM`/`NAPMPI`/`NAPMEI`）已全部下線，回 404** | 你指定的四大宏觀指標之一**無法取得**。必須改用替代指標，或明確標示「不提供」 |
| 2 | **港股在 SEC EDGAR 完全沒有申報（`.HK` 代碼 0 筆）** | 財報模組對 154 檔池子裡的 **70 檔港股完全無效**，只能覆蓋 84 檔美股 |
| 3 | **FRED 有免 Key 的 CSV 入口（`fredgraph.csv`），但 API 必須 Key** | 可以「零設定」先上線，Key 只是取得 metadata 與更嚴謹的錯誤處理 |

另外一個必須先講的架構問題：**這個頁面有一半的模組不是「個股頁」**。宏觀利率、FOMC 會議、ISM、赤字、匯率都是全市場共用的資料，放進「個股詳情」會導致同一份資料被重複抓取 N 次。下面 §1 會處理這個矛盾。

## 一、頁面資訊架構

### 1.1 先解決一個設計矛盾

你的需求是「在現有股票頁面中新增一個整合頁」，但三個模組的**資料粒度不同**：

| 模組 | 資料粒度 | 是否隨個股變動 |
|---|---|---|
| 一、個股新聞 | 個股 | ✅ 是 |
| 二、財報基本面 | 個股 | ✅ 是 |
| 三、宏觀利率與指標 | 全市場 | ❌ 否 |

如果做成單一頁面且全部隨 symbol 重抓，會出現「換一檔股票就重打一次 FRED + FOMC」的浪費。**FRED 免費 Key 的速率限制是 120 req/min**，選股頁一次跑 154 檔就會撞牆。

**建議架構：一個導覽入口，兩種作用域。**

```
#/macro              宏觀頁（全市場，不帶 symbol）      ← 模組三
#/macro/AAPL         整合頁（帶 symbol）                ← 模組一＋二＋三摘要
```

- `#/macro` 不帶代碼時，只顯示模組三（宏觀），並提示「輸入代碼可看個股層面的整合」
- `#/macro/AAPL` 三個模組全上，模組三降級為「宏觀背景」精簡卡（只留 3 個最相關指標）
- 這樣宏觀資料可以**跨個股共用同一份快取**，換股票不重打 FRED

### 1.2 站點地圖（含既有頁面）

```
導覽列 mainNav
├── K 線預測        #/predict            既有
├── AI 選股         #/screen             既有
├── 宏觀與基本面     #/macro              ← 新增（本次）
└── 個股詳情        #/detail/:symbol     既有（隱藏項，進入才顯示）

新增的兩條路由
├── #/macro                 全市場宏觀儀表板（無 symbol）
└── #/macro/:symbol         個股整合頁（新聞＋財報＋宏觀背景）
```

**與既有路由的關係**：`#/detail/:symbol` 與 `#/macro/:symbol` 都是「帶代碼的頁面」，但用途不同——前者是技術面（買區、K 線、預測），後者是基本面與消息面。兩者之間**互相加交叉連結**，而不是合併：

- 個股詳情頁底部加一行「→ 看 AAPL 的財報與新聞」
- 宏觀整合頁頂部加一行「→ 回 AAPL 的技術面分析」

理由：技術面與基本面的更新頻率、資料來源、失敗模式完全不同，混在同一頁會讓「K 線載入失敗」與「SEC 逾時」互相牽連。分頁 + 互連，職責清楚。

## 二、各模組的資料欄位與來源對應

### 2.1 模組一：個股相關財經新聞

#### 實測：可用來源與新鮮度

我實打了 10 個來源，結果差異極大。**注意「HTTP 200」不等於可用**：

| 來源 | 狀態 | 筆數 | 最新一筆 | 判定 |
|---|---|---|---|---|
| **MarketWatch Top Stories** | 200 | 10 | **當天** | ✅ 主力來源 |
| **Fed 新聞稿 RSS** | 200 | 20 | **當天** | ✅ 宏觀政策消息 |
| **Fed 貨幣政策 RSS** | 200 | 15 | 1 天前 | ✅ 政策解讀 |
| **SEC 8-K Atom** | 200 | 10 | **當天** | ✅ 個股重大事件 |
| WSJ Markets RSS | 200 | 20 | **2025-01-27（落後 667 天）** | ❌ **已停更，不可用** |
| CNBC RSS | 403 | — | — | ❌ 擋爬 |
| Yahoo 新聞 RSS | 429 | — | — | ❌ 限流 |
| Reuters RSS | DNS 失敗 | — | — | ❌ 端點已撤 |
| AP Business | 403 | — | — | ❌ 擋爬 |
| Nasdaq RSS | 逾時 | — | — | ❌ 不穩 |

**這是本模組最重要的發現**：WSJ 那個 feed 回 200 但內容停在 2025 年 1 月。如果只看狀態碼就接入，使用者會看到兩年前的新聞，而且**畫面完全正常、不會報錯**。所以實作時必須加「新鮮度檢查」——見 §3.4。

#### 欄位對應

| 前端欄位 | 型別 | 來源 | 說明 |
|---|---|---|---|
| `title` | string | RSS `<title>` | 標題，需去 CDATA 與 HTML 實體 |
| `url` | string | RSS `<link>` | 原文連結，`target="_blank" rel="noopener"` |
| `source` | string | 人工映射 | 「MarketWatch」「聯準會」「SEC」 |
| `sourceTier` | enum | 人工映射 | `primary`（一級權威）／`filing`（申報文件） |
| `publishedAt` | ISO string | RSS `<pubDate>` | **必做時區正規化**，RSS 多為 -0500 |
| `ageHours` | number | 計算 | 前端顯示「2 小時前」 |
| `summary` | string | RSS `<description>` | 截斷 120 字，去標籤 |
| `relatedSymbol` | string \| null | 比對 | 標題含代碼或公司名時標記 |
| `relevance` | enum | 計算 | `symbol`（明確相關）／`sector`（產業）／`macro`（宏觀） |

#### 「個股相關」怎麼判定

Yahoo 現有的 `news()` 是「用代碼查 Yahoo 搜尋 API」，這條路在 Render 上回 429。新版改用**關鍵詞比對**：

1. 取公司名（SEC `company_tickers.json` 的 `title`，或既有 alias 表）去除 `Inc.`/`Corp.`/`Ltd.` 等後綴
2. 標題或摘要含「代碼」或「公司名主體」→ `relevance: symbol`
3. 否則歸入 `macro`（宏觀新聞對所有股票都有意義）

**重要限制**：這是「標題字串比對」，不是真正的語意相關性判斷。好處是零依賴、可解釋、不會幻覺；壞處是「Apple 這家水果公司」也會被算成相關。**寧可漏，不要錯**——這是本頁的取捨原則。

### 2.2 模組二：企業財報與基本面

#### 實測：SEC EDGAR 三個端點

**User-Agent 要求（已實測）**：必須帶 `User-Agent: 應用名 聯絡信箱`。不帶會回 403。

| 端點 | 用途 | 實測結果 |
|---|---|---|
| `/files/company_tickers.json` | 代碼 → CIK 映射 | 200，**10,400 筆**，796KB，0.12s |
| `/api/xbrl/companyfacts/CIK##########.json` | 全部財務事實 | 200，**3.86MB**，2.0s，AAPL 有 512 個概念 |
| `/submissions/CIK##########.json` | 申報清單 | 200，165KB，0.09s，**1,007 筆**近期申報 |

**速率限制實測**：連發 12 次全部 200，**未觸發限速，也沒有 `x-ratelimit-*` 標頭**。但官方明文規定 10 req/s，且會封鎖違規者。**不能因為「測不出來」就放飛**——必須自建節流器（§3.3）。

#### ⚠️ 兩個必須寫進程式碼的陷阱

**陷阱 1：`Revenues` 這個概念已廢棄。**
實測 AAPL 的 `Revenues` 只有 11 個資料點，**最新停在 2018-09-29**；現行財報用的是 `RevenueFromContractWithCustomerExcludingAssessedTax`（120 點，最新 2026-09-26）。

如果照文件直覺寫 `facts['us-gaap'].Revenues`，會拿到 8 年前的營收，而且**完全不報錯**。必須用「概念優先序」逐個嘗試：

```
營收：RevenueFromContractWithCustomerExcludingAssessedTax
      → Revenues
      → RevenueFromContractWithCustomerIncludingAssessedTax
      → SalesRevenueNet
淨利：NetIncomeLoss → ProfitLoss
EPS ：EarningsPerShareDiluted → EarningsPerShareBasic
毛利：GrossProfit
營業利益：OperatingIncomeLoss
資產：Assets ｜ 負債：Liabilities ｜ 權益：StockholdersEquity
```

**陷阱 2：同一概念有多種「期間語義」混在一起。**
`Assets` 是**時點值**（`frame: CY2026Q3I`，I = instant），而 `Revenues` 是**區間值**（有 `start`/`end`）。混用會把「單季」與「累計 9 個月」當成同一條序列，算出來的 YoY 完全是錯的。

過濾規則：
- 只取 `form` 為 `10-K` 或 `10-Q`
- 用 `(end - start)` 天數判斷期間：`≈90 天` → 單季、`≈365 天` → 年度
- 同一 `(start, end)` 若有多次申報，取 `filed` 最新的一筆（重述以最新為準）

#### 欄位對應

| 前端欄位 | 來源概念 | 期間處理 |
|---|---|---|
| 營收 TTM | `RevenueFromContractWithCustomerExcludingAssessedTax` | 最近 4 個單季相加 |
| 營收 YoY | 同上 | 本期 TTM vs 去年 TTM |
| 淨利 TTM | `NetIncomeLoss` | 最近 4 個單季相加 |
| 毛利率 | `GrossProfit / Revenue` | 同期配對，勿跨期 |
| 營業利益率 | `OperatingIncomeLoss / Revenue` | 同期配對 |
| 稀釋 EPS | `EarningsPerShareDiluted` | 直接取最近年度值 |
| 總資產 / 總負債 / 權益 | `Assets` / `Liabilities` / `StockholdersEquity` | 取最新時點值 |
| 負債比 | `Liabilities / Assets` | 同時點 |
| ROE | `NetIncomeLoss(TTM) / StockholdersEquity` | 分子期間、分母時點，**需標註算法** |
| 本益比 | 需要市值 | 取自既有 `/api/analyze` 的 `meta.price` × 流通股數 |
| 最近申報 | `/submissions` 的 `form`/`filingDate`/`accessionNumber` | 篩 10-K/10-Q/8-K，取前 10 |

**台港股票怎麼辦**：`BRK.B` 這種帶點的代碼在 SEC 表裡是 `BRK-B`（實測確認），需做代碼正規化。港股則**完全沒有**（`\.HK$` 匹配 0 筆），必須走降級路徑。

### 2.3 模組三：宏觀利率與指標

#### 實測：FRED 兩種取法

| 方式 | 需要 Key | 實測 | 建議 |
|---|---|---|---|
| `api.stlouisfed.org/fred/series` | ✅ 必須 | 無 Key 回 **400**，訊息明確要求 `api_key` | 有 Key 時用，可取 metadata |

#### FOMC 會議日程實測

來源：`federalreserve.gov/monetarypolicy/fomccalendars.htm`，200，166KB。

**可靠解析法**：用 `monetaryYYYYMMDDa.htm` 這種 URL 命名規則提取會議日期（`a` 後綴通常是會後聲明）。實測從同一頁面可提取 **48 個聲明日期，涵蓋 2021–2026**，2026 年完整 7 場：

```
2026-01-28, 2026-03-18, 2026-04-29, 2026-06-17,
2026-07-29, 2026-09-16, 2026-10-28
```

**⚠️ 解析陷阱**：實測 2025 年多出一筆 `2025-08-22`，那是 **Jackson Hole 全球央行年會，不是 FOMC 例會**。若直接全部收下，會誤報一場不存在的利率決議。必須過濾：
- 每年 FOMC 例會為 **8 場**（實測 2021–2024 皆是 8 場），2026 頁面僅列 7 場（12 月那場可能尚未建連結）
- 用「同年度取前 8 場」+ 排除 8 月下旬（Jackson Hole 時段）
- 或更嚴謹：只認 `fomccalendars.htm` 頁面中的會議表格，不從 `pressreleases` 連結反推

> 實務建議：第一次實作時，把解析結果與 Fed 官網頁面人工比對一次，並把「預期場次數」寫成斷言（每年 8 場），場次數不符就報警而非靜默接受。

#### 利率預測怎麼做（這是本模組最需要說清楚的部分）

你的需求寫「依據 FED 定義會議與利率預測」。實測結果：**Fed 官方不發布利率預測路徑**（點陣圖是與會者匿名預測，非委員會決議），而市場用的 CME FedWatch 需要期貨結算價，其網站在本環境**不可達（連線逾時）**。

所以「利率預測」只有三條現實可行的路：

| 方案 | 資料來源 | 可信度 | 實作難度 |
|---|---|---|---|
| **A. 目標區間 + 會議日程（建議）** | `DFEDTARU`/`DFEDTARL` + FOMC 日曆 | ✅ 全部是官方事實 | 低 |
| B. 期貨隱含機率 | 需 CME 或聯邦基金期貨價 | ⚠️ 需第三方，且 CME 站不可達 | 高 |
| C. 自行外推 | 用歷史目標利率線性外推 | ❌ **不建議，會誤導** | 低 |

**強烈建議只做 A，把「預測」定義為「已知的會議時程 + 當前的利率水準」**，而不是「未來利率會走到哪」。理由：

1. 任何自行產生的利率預測都無法驗證，且會讓使用者以為是 Fed 的官方預期
2. 這與你在 K 線預測模組已確立的原則一致——**「寧可沒有預測，也不要錯的預測」**
3. 若真的要市場預期，應標示「期貨隱含機率」並附資料時間，且需另找可達的資料源（目前無）

如果未來要加 B，介面要預留 `impliedProbability` 欄位但**預設為 `null`**，前端顯示「暫無資料」，而不是顯示 `0%`。

## 三、資料更新頻率與快取策略

### 3.1 各資料的天然更新頻率（先尊重資料本身）

| 資料 | 原始更新頻率 | 說明 |
|---|---|---|
| 日頻利率（DGS10 等） | 每交易日收盤後 | 週末與假日無新值 |
| 月頻（CPI/UNRATE/INDPRO） | 每月一次 | 發布日固定但不規則 |
| 財政赤字（月度） | 每月 | 月結後約 2 週 |
| SEC 財報 facts | 每季（10-Q）／每年（10-K） | 但「申報清單」每天有新 8-K |
| FOMC 日程 | 每年公布一次年度表 | 內容幾乎不變 |
| 新聞 | 隨時 | 分鐘級 |

**原則：快取 TTL 不應短於資料本身的更新頻率。** 日頻資料設 5 分鐘 TTL 是浪費——它在收盤前根本不會變。

### 3.2 建議的 TTL 分層

| 資料類型 | TTL | 理由 |
|---|---|---|
| 新聞 | **15 分鐘** | 與既有 `yahoo.news()` 的 15 分鐘一致，避免兩套標準 |
| 日頻利率序列 | **6 小時** | 一天最多更新一次，6 小時足夠且大幅省請求 |
| 月頻宏觀序列 | **24 小時** | 一個月才變一次 |
| SEC `companyfacts` | **24 小時** | 財報季才變，3.86MB 不宜頻繁抓 |
| SEC `submissions` | **6 小時** | 8-K 隨時可能出現 |
| **SEC ticker→CIK 映射** | **7 天** | 幾乎不變，796KB |
| FOMC 日程 | **7 天** | 年度表，幾乎不變 |
| 新聞源可用性檢查 | **10 分鐘** | 記錄「哪個源死了」，避免每輪都打死亡源 |

### 3.3 三層快取（沿用專案既有模式）

專案在 `lib/screener.js` 已建立「記憶體 → 落地檔」的模式，本頁沿用：

```
L1 記憶體（Map）
  └─ 命中率最高，單次請求內與跨請求共用
L2 落地檔（data/macro/*.json）
  └─ 跨進程重啟保留；Render 免費方案休眠後喚醒仍有資料
L3 「僅成功才落盤」原則
  └─ 抓取失敗不覆寫既有快取，避免一次上游故障把好資料洗掉
```

**SEC 專用的節流器（必須做）**：

```js
// 全域單一併發上限，不隨請求數膨脹
// 理由：154 檔池子若每檔都抓 facts，3.86MB × 154 = 594MB，且必撞 10 req/s
const SEC_LIMITER = { minIntervalMs: 120, lastAt: 0 };  // 約 8.3 req/s，留安全邊際
```

**關鍵設計**：SEC 的 `companyfacts` **只在單一個股頁抓取**，選股頁**絕不**批次抓。若要支援「選股結果加基本面欄位」，必須另建離線預抓任務（見 §4.4），不能在使用者請求路徑上做。

**FRED 的批次最佳化（已實測可行）**：`fredgraph.csv` 支援用**逗號**合併多序列：

```
?d=DGS10,DGS2  →  HTTP 200，回傳三欄 CSV：
                  observation_date,DGS10,DGS2
                  1962-01-02,4.06,
                  1962-01-03,4.03,
```

實測 `DGS10,DGS2` 合併後 338KB / 16,932 列，能把 20 個序列壓成 **2–3 次請求**。

⚠️ **兩個實作細節（實測踩到）**：
1. 分隔符必須是**逗號**。用 `?id=DGS10&id=DGS2` 只會取最後一個（實測只回 `DGS2`）。
2. **合併後會有大量空值**：實測 16,932 列中有 **4,314 列含空值**，因為各序列的歷史起點不同（DGS2 從 1976 年才有，DGS10 從 1962 年）。解析時必須把空字串視為 `null`，**不能當成 0**——否則畫圖會出現掉到 0 的假線。


### 3.4 新鮮度守門（針對 WSJ 那類「200 但停更」的坑）

每個源都記錄 `lastItemAt`，並在回傳前檢查：

```
若 (now - lastItemAt) > 該源預期最大間隔（新聞類 7 天）
  → 標記 sourceHealth: 'stale'
  → 前端不顯示該源，或顯示「此來源可能已停更」
  → 絕不靜默當成正常
```

這一條直接對應 WSJ 落後 667 天的實測結果。**沒有這道守門，接入一個停更的源是無感的**。

### 3.5 失敗處理分級（沿用專案既有的三種「不可用」區分）

專案在 GEX 模組已建立這個原則，這裡直接沿用：

| 情況 | 標記 | 前端文案 | 重試 |
|---|---|---|---|
| 404（ISM 下線） | `unavailable: 'retired'` | 「此指標已停止公開提供」 | ❌ 重試無用，明確告知 |
| 403/429 | `unavailable: 'blocked'` | 「來源限制存取」 | ⚠️ 可能稍後恢復 |
| 逾時／連線失敗 | `unavailable: 'transient'` | 「暫時無法取得，請稍後重試」 | ✅ 可重試 |
| 港股查 SEC | `unavailable: 'not_applicable'` | 「港股無 SEC 申報」 | ❌ 本來就沒有 |
| 抓到但資料過舊 | `unavailable: 'stale'` | 「資料已停止更新（最後 X）」 | ⚠️ 視來源而定 |

**這五種不能混為一談。** 混在一起，使用者會反覆重試一個註定失敗的模組（專案已踩過這個坑）。

SA.onRoute({

});

需要在 `common.js` 的 `parseHash()` 加入 `macro` 路由解析，並在 `dispatch()` 增加分支。**這是本次唯一需要改動既有檔案的邏輯點**，改動量小。

### 4.4 選股頁要不要加基本面欄位？

- `#/screen` 一次掃 154 檔，若每檔抓 SEC facts（3.86MB × 84 檔美股）→ 324MB 流量、且必撞 10 req/s

## 六、潛在限制（全部基於實測，非推測）

### 6.1 無法繞過的硬限制

| # | 限制 | 實測證據 | 影響 |

| L1 | **ISM 製造業指數已下線** | `NAPM`/`NAPMPI`/`NAPMEI` 全回 404 | 四大宏觀指標缺一，需替代方案 |
| L2 | **港股無 SEC 申報** | `\.HK$` 匹配 **0 筆** | 154 檔中 **70 檔（45%）** 財報模組無效 |
| L3 | **Fed 不發布利率預測路徑** | 點陣圖是匿名預測非決議 | 「利率預測」只能做「已知時程＋當前水準」 |
| L4 | **CME FedWatch 不可達** | 連線逾時（000） | 無法取得期貨隱含機率 |

### 6.2 需要設計妥協的限制

| # | 限制 | 妥協方式 |
|---|---|---|
| L7 | SEC `companyfacts` 單檔 **3.86MB** | 只在個股頁抓，不快取全池；用 gzip（實測 SEC 支援） |
| L8 | SEC 限 10 req/s | 自建節流器（120ms 間隔），選股頁絕不批次抓 |
| L9 | 同一概念多種期間語義混雜 | 用 `start`/`end` 天數判定單季/年度，並寫單元測試鎖定 |
| L10 | `Revenues` 已廢棄但仍在 API 裡 | 概念優先序，且**驗證最新資料點的日期**，太舊就往下試 |
| L11 | 台港代碼格式差異 | `BRK.B` → `BRK-B`；`.HK` 直接走降級 |
| L12 | 新聞相關性只能靠字串比對 | 明確標示「以關鍵詞比對」，寧漏不錯 |
| L13 | FRED 多序列合併後有大量空值 | 實測 16,932 列中 4,314 列含空值（各序列起點不同）；空字串須視為 `null`，**不可當 0**，否則圖表會出現假跌到 0 的線段 |

### 6.3 環境特定的限制

| # | 限制 | 說明 |
|---|---|---|
| L14 | WorkBuddy 沙箱出網受限 | 已知僅騰訊可達。**此頁在沙箱上大部分模組會不可用**，需靠 Render |
| L15 | Render 免費方案 15 分鐘休眠 | 冷啟動 30–60 秒；落地檔快取在此特別有價值 |
| L16 | Render 免費方案**無持久磁碟** | `data/` 在重新部署後會清空 → 快取是「盡力而為」，不能當唯一資料來源 |

L16 特別值得注意：專案既有的 `data/picks/` 也是同樣情況。所以快取策略必須是「**快取失效就重抓**」，而不是「快取是主要資料」。

### 6.4 法律與合規

| 項目 | 狀態 |
|---|---|
| SEC EDGAR | ✅ 公開資料，要求 User-Agent 聲明聯絡方式（**必須遵守**，否則 403） |
| FRED | ✅ 公開，多數序列可自由使用；**部分序列有版權限制**（如 ISM 就是因此下架），使用前需確認 |
| RSS 新聞 | ⚠️ **只顯示標題＋連結回原文，不轉載全文**。這是媒體 RSS 的通用禮儀與法律邊界 |
| 新聞摘要 | ⚠️ 建議只顯示前 120 字並標明來源，避免被視為轉載 |

**Redistribution 提醒**：FRED 的資料多數可自由散布，但「轉售」有限制。若這個應用未來要商業化，需逐一確認每個序列的授權條款。

# K 線預測與 AI 選股規格書 v1.0

> **定位**：本文件是「K 線預測」（以下簡稱 FP）與「AI 選股」（以下簡稱 AS）兩項新功能的**開發與驗收依據**。
> **性質**：只定義**範圍、輸入、輸出、參數、邊界、驗收標準與假設**，不含實作程式碼。
> **基線**：以 2026-11-25 實際運行 `stock-entry-analyzer`（commit `c685a01` 之後的本地工作區）的輸出為準，所有「現有功能」描述均經執行驗證，非依文件推測。
> **編號**：`FP-n`＝K 線預測條目；`AS-n`＝AI 選股條目；`GAP-n`＝盤點時發現的既存缺陷；`AC-nn`＝驗收標準。
> **圖例**：`[新增]` 全新模組／`[擴充]` 在既有模組上加欄位／`[相依]` 依賴其他條目完成／`[待確認]` 需業主裁決。

## 0. 現有系統功能盤點（實測）

盤點目的只有一個：**確認新功能不會與既有功能重複定義同一件事**。以下每一項都經實際呼叫驗證。

### 0.1 對外介面現況

| 端點 | 方法 | 現況 | 實測結果 |
|---|---|---|---|
| `/api/health` | GET | 健康檢查 | 200 |
| `/api/config` | GET | 回傳 Telegram 是否已設定 | 200 |
| `/api/search?q=` | GET | 代碼／名稱搜尋；中文走本地索引 | 200 |
| `/api/analyze?symbol=` | GET | **單一標的完整分析**（核心端點） | AAPL 576ms / 56,444 bytes；0700.HK 435ms / 46,699 bytes |
| `/api/news?symbol=` | GET | 相關新聞 | 200 |
| `/api/notify` | POST | 發送 Telegram 通知 | 200（模擬模式可用） |
| `/api/diag/*` | GET | 6 個除錯端點（source/kline/url/hdr/probe） | 200 |

**關鍵事實 1**：系統**只支援單一標的查詢**（`?symbol=一個代碼`），**不存在**「一次回傳多標的清單」的端點，也**不存在**首頁行情列表。第 9 項要求的「首頁顯示每日選股清單」是**全新的頁面區塊**，不是既有元件的改版。

**關鍵事實 2**：無任何持久化。全域搜尋 `fs.writeFile` / 資料庫依賴 → 僅有 `config.json` 讀取。**沒有資料庫、沒有快取落地、沒有歷史預測存檔**。這直接決定第 4 項「上線後監測」與第 7 項「排程」必須先建持久層。

**關鍵事實 3**：無任何排程器。全域搜尋 `setInterval` / `cron` / `schedule` → **0 筆**。第 7、9 項的「每日執行」需要從零建立。

**關鍵事實 4**：無任何 AI／LLM 呼叫。搜尋 `openai|gemini|anthropic|deepseek` → **0 筆**。第 9 項是完全新增的外部依賴。

### 0.2 現有分析輸出（`/api/analyze` 實際回傳）

頂層欄位 16 個：`meta, verdict, score, scoreBreakdown, snapshot, levels, buyZone, rationale, probabilities, backtest, series, advancedTools, dataUpdatedAt, dataSource, dataSourceKey, ok`

其中與「預測」語義最接近的是 **`probabilities`**，實測 AAPL：

```json
{
  "confidence": "medium", "sampleSize": 29,
  "probUp10": 0.6053, "probUp20": 0.6796, "probProfit": 0.6891,
  "baseRate20": 0.6279, "edge20": 0.0644
}
```

以及 **`backtest`**（10／20 日雙視窗）：

```json
{"samples":29,"pending":0,
 "horizons":{
   "10":{"n":29,"winRate":0.5862,"avgReturn":-0.1899,"medianReturn":1.3396,
         "avgWin":2.806,"avgLoss":-4.4341,"mfe":3.5908,"mae":-3.6154,
         "baseRate":0.5866,"edge":-0.0004},
   "20":{"n":26,"winRate":0.6923,"avgReturn":-0.1531,"medianReturn":2.0458,
         "avgWin":2.7671,"avgLoss":-6.7234,"baseRate":0.6279,"edge":0.0644}}}
```

**這是最大的設計風險點**：既有 `probabilities` 已經是「未來 10／20 日上漲機率」。若 FP 也輸出「上漲機率」，就是**同一個數字被定義兩次**，且兩者算法不同（見 §1 GAP-1），使用者必然混淆。本規格以 §2.1 的「差異對照表」強制分界。

### 0.3 既有回測機制的實際邏輯（必須理解才能定邊界）

`lib/analyzer.js` 的 `backtest()` 做的事：

1. 取日線 **2 年**（`chart(symbol,'2y','1d')`），約 250 根。
2. 對每根 K 線判斷是否「觸及買入區間」：`c.low <= upper && c.high >= lower`。
3. 觸及則視為進場（成交價 `clamp(close, lower, upper)`）。
4. 往後看 10／20 根，計算報酬率、MFE／MAE、勝率。
5. 另算**基準普及率**（所有時點的 20 日正報酬率）作為對照。

**已確認的三個特性**：

- 這是**條件式回測**（只在「觸及買入區」時取樣），**不是**連續預測。AAPL 兩年只取到 29 個樣本。
- 勝率**未扣除交易成本與滑價**。
- 樣本推進度不足時標為 `pending`，不計入勝率（設計正確）。

## 1. 盤點發現的既存缺陷（阻擋項）

這五項不是新功能的需求，但**會直接讓新功能算出錯誤結果**，必須先修或明確繞過。列在此處是為了讓驗收方知道「為什麼某些驗收標準會失敗」。

| 編號 | 缺陷 | 證據 | 對新功能的影響 |
|---|---|---|---|
| **GAP-1** | `probabilities` 的算法是**啟發式混權**，非統計模型 | `probUp20 = histWin × w + (score/100) × (1−w)`，`w = clamp(n/40, 0.25, 0.7)`。把「技術面評分」直接當機率混入 | FP 若也輸出機率，兩者必然不一致且無法解釋差異 |
| **GAP-2** | 取價**未復權**，跨除權日報酬失真 | `lib/yahoo.js:244` 只用 `indicators.quote[0].close`；`events=div,split` 只是請求事件參數，**未用於調整價格** | 回測與預測在除權日附近會出現假的暴跌／暴漲 |
| **GAP-3** | `targetProb` 是死代碼 | `lib/analyzer.js:481`：`clamp(0.5, 0.1, 0.9)` → **恆等於 0.5**（參數順序錯誤，回傳 lo 而非限幅值）；且該欄位**未出現在輸出** | 目標價達成機率目前**完全沒有**，FP 可填補此空缺 |
| **GAP-4** | 勝率未計交易成本 | `backtest()` 直接用 `(exit−entry)/entry` | FP 驗收若要求「可實作績效」，需明訂成本假設 |
| **GAP-5** | 前端無「清單／列表」容器 | `#welcome` 是靜態歡迎卡；`#result` 是單一標的結果區 | AS 的「首頁清單」須新建容器，且不得破壞既有 `hidden` 切換邏輯 |

> **GAP-2 補充說明**：Yahoo 的 chart API 另有 `indicators.adjclose` 欄位可用，但現行解析完全沒讀。這不是「資料不可得」，是「沒取用」。

## 2. 差異對照表

### 2.1 FP（K 線預測）vs 現有功能

**核心分界原則**：現有 `probabilities` 回答**「歷史上，價格來到這個區間後，未來 20 天漲的機率有多高」**（條件式、事後統計）。FP 回答**「從今天這個收盤價出發，未來 N 天的價格區間會落在哪裡」**（無條件、前瞻區間）。兩者**輸入條件不同、時間原點不同、輸出型態不同**，因此不構成重複。

| 維度 | 現有 `probabilities` | 現有 `backtest` | 現有 `buyZone` | **FP 預測值** | 關係判定 |
|---|---|---|---|---|---|
| 回答的問題 | 觸及買區後 20 日上漲機率 | 觸及買區後的歷史績效分布 | 該在哪個價位買 | 未來 N 日**價格區間**與**方向傾向** | **不重複**：原點不同 |
| 時間原點 | 歷史每一根觸及 K 線 | 歷史每一根觸及 K 線 | 當前 | **僅當前最後一根收盤** | 不重複 |
| 是否條件式 | 是（須觸及 buyZone） | 是（須觸及 buyZone） | — | **否**（任何標的皆可預測） | 不重複 |
| 輸出型態 | 機率純量 0–1 | 績效統計表 | 價格區間＋停損目標 | **價格區間＋方向機率＋信賴區間** | 部分重疊（皆有區間），見 §2.3 |
| 數值可否互換 | `probUp20` ≠ FP 方向機率 | 回測勝率 ≠ FP 命中率 | `upper/lower` ≠ FP 區間 | **不可互換，不得互相推導** | 見 §2.4 換算禁令 |
| 樣本不足時 | 退回 `score×0.85` 並夾在 0.25–0.78 | 樣本 <5 顯示信心不足 | 一律給出區間 | **明確輸出 `insufficient`，不給數值** | 不衝突 |

### 2.2 AS（AI 選股）vs 現有功能

| 維度 | 現有 | **AS 選股** | 關係判定 |
|---|---|---|---|
| 查詢模式 | 使用者輸入**一個**代碼 | 系統**每日自動**產出 N 檔清單 | **不重複**：輸入端相反 |
| 標的範圍 | 任意使用者指定 | **限定在本地索引 154 檔池內**（見 §10.5） | 需明確界定，否則無法保證可分析 |
| 排序依據 | 無（單一結果） | FP 分數＋流動性＋風險三重排序 | 新增 |
| 輸出位置 | `#result`（查詢後） | **首頁新區塊**（`#welcome` 旁，見 §10.6） | 新增，不覆蓋既有 |
| 是否呼叫 LLM | 否 | **是**（唯一外部 AI 依賴） | 全新 |
| 資料流 | 即時抓取 | 預先計算＋快取落地 | 全新 |

### 2.3 明確標示「部分重疊」的區塊

以下三處**必須在 UI 上做視覺區隔**，否則使用者會誤讀：

1. **區間數字重疊**：`buyZone.lower/upper`（進場區間）與 FP 預測區間可能落在相近價位。**裁決**：FP 區間一律以「未來 N 日預測範圍」措辭呈現，禁止使用「買入」二字；UI 上 FP 區間**不得**使用與 `buyZone` 相同的藍色底帶（`COLORS.zone`），改用中性虛線框（見 §7.3）。
2. **機率數字重疊**：`probUp20` 與 FP 方向機率並存。**裁決**：兩者**同屏出現時必須加註來源標籤**，且不得並排放在同一張卡片（見 §7.4）。
3. **「目標價」重疊**：`buyZone.target`（獲利目標）與 FP 預測上界。**裁決**：`buyZone.target` 維持原義（策略目標），FP 上界改稱「預測壓力上界」，**禁止**標示為「目標價」。

### 2.4 換算禁令（不可違反）

> **FP-0（強制條款）**：FP 的任何輸出值，**不得**由 `probabilities`、`backtest.horizons`、`buyZone` 任一欄位透過公式轉換得出。FP 必須有**獨立計算管線**。
>
> **反向亦然**：`probabilities` 與 `backtest` 的既有值**不得**因 FP 上線而變動。驗收時以「FP 上線前後的 `probabilities` 逐位元相同」為判準（見 AC-01）。

理由：兩者統計母體不同（條件式 vs 無條件），任何互換都會產生**看似合理但無統計意義**的數字。

## 3. FP-1 預測目標

### 3.0 六要素速查

| 要素 | 內容 | 詳見 |
|---|---|---|
| 功能範圍 | 單一標的、預測收盤價、週期 5/10/20 交易日、三檔並列 | §3.1 |
| 輸入 | `/api/analyze` 解析後的 symbol ＋ 日線 candles（經 §4 前處理） | §4 |
| 輸出 | `pred.horizons[h] = {q10,q25,q50,q75,q90,p_up,p_target}` | §3.3 |
| 必要參數 | `horizons=[5,10,20]`、`lookback≤500`、`minSamples=250`、`seed=20261125` | §3.3 |
| 邊界條件 | <250 根→`insufficient`；停牌→`stale`；ETF→標示；除權未修→`blocked` | §3.4 |
| 驗收標準 | AC-01–AC-06（6 項） | §3.5 |
| 待確認假設 | A-01–A-04（4 項） | §3.6 |
| 相依項目 | GAP-2 復權修復、§4 模型選型、§10.2 批次端點 | §3.7 |


### 3.1 功能範圍

| 項目 | 規格 |
|---|---|
| 預測標的 | 使用者當前查詢的**單一**標的（沿用 `/api/analyze?symbol=` 的解析結果，含中文別名、模糊比對） |
| 預測對象 | **收盤價**（`c`）。不預測開高低、不預測成交量、不預測波動率 |
| 預測週期 | **三檔並列輸出**：`h=5`、`h=10`、`h=20`（交易日，非日曆日） |
| 為什麼是這三檔 | 與既有 `backtest` 的 10／20 對齊（可比對），另加 5 日以覆蓋短線情境；**不提供** 1 日與 60 日以上（1 日噪音主導，60 日超出 2 年資料的樣本效率） |
| 業務目的 | ①告訴使用者「未來 N 日的合理價格範圍」；②為 AS 提供跨標的**可比較的分數**；③填補 GAP-3（目標價達成機率缺失） |
| 使用情境 | ①使用者查完技術位後，判斷「現在進場，5/10/20 日後的收盤價區間落在何處」；②AS 每日批次對 154 檔產生分數並排序 |

### 3.2 預測值與現有指標的定義差異

| 概念 | 現有定義 | FP 定義 | 差異說明 |
|---|---|---|---|
| 「上漲機率」 | `probUp20`：**觸及買區**後 20 日收盤 > 進場價的歷史比率，再與 `score` 混權 | `p_up(h)`：**今日收盤**起算，h 日後收盤 > 今日收盤的機率 | 原點不同（進場價 vs 今日收盤）、母體不同（條件 vs 無條件） |
| 「區間」 | `buyZone.lower/upper`：**建議買入**價位帶 | `[q10, q90]`：未來 h 日收盤價的 **10%–90% 分位** | 前者是「該買在哪」，後者是「可能走到哪」，語義不相交 |
| 「目標價」 | `buyZone.target`：策略獲利目標（`resistances[0]` 或 `upper+3×ATR`） | `p_target`：h 日內**曾触及** `buyZone.target` 的機率 | 前者是價位，後者是機率。**此欄位取代 GAP-3 的死代碼** |
| 「勝率」 | `backtest.horizons[h].winRate` | **不輸出**。FP 不談勝率 | 避免與回測勝率混淆；勝率屬「策略回測」語義 |

### 3.3 必要參數

```json
{
  "horizons": [5, 10, 20],          // 固定，不可由前端指定
  "lookback": 500,                   // 用於擬合模型的歷史 K 線根數上限
  "minSamples": 250,                 // 低於此值輸出 insufficient
  "quantiles": [0.1, 0.25, 0.5, 0.75, 0.9],
  "seed": 20261125                   // 亂數種子（若採蒙地卡羅）
}
```

### 3.4 邊界條件

| 情境 | 行為 |
|---|---|
| 可取得日線 < 250 根 | `status: "insufficient"`，附 `reason`、`available`。**不輸出任何機率或區間數值** |
| 250 ≤ 根數 < 500 | 正常計算，`quality` 標為 `low`，`lookback` 取實際根數 |
| 標的停牌／當日無成交 | 沿用最後有效收盤，`stale: true` 並附 `lastBarDate` |
| 標的為 ETF／指數 | 允許計算，`assetClass` 標示，UI 加註「非個股，預測僅供參考」 |
| 標的剛上市（<250 根） | 同第一列，`insufficient` |
| 拆分／除權日落在預測窗內 | 見 GAP-2；FP 上線前**必須**先修復復權，否則 `status: "blocked"` 並提示 |

### 3.5 驗收標準

| 編號 | 標準 | 判定方式 |
|---|---|---|
| AC-01 | FP 上線後，`probabilities` 與 `backtest` 的輸出與上線前**逐欄位相同** | 同一標的（AAPL）同日兩次呼叫，比對 JSON 深度相等 |
| AC-02 | `insufficient` 時，回應中**不含** `p_up`、`q10`、`q90`、`p_target` 任一鍵 | 以不存在的代碼（如 `ZZZZ`）測試，檢查 key 不存在（非 `null`） |
| AC-03 | 三檔週期齊備，key 恰為 `5,10,20` | `Object.keys(pred.horizons).sort()` 深度等於 `["10","20","5"]` |
| AC-04 | `q10 ≤ q25 ≤ q50 ≤ q75 ≤ q90` 恆成立 | 對 154 檔全跑一次，違反者 0 筆 |
| AC-05 | `0 ≤ p_up ≤ 1` 且非 `null`／`NaN` | 全池掃描 |
| AC-06 | 輸出**不含**「勝率」「winRate」字樣 | 檢查 `pred` 子樹無此 key |

### 3.6 待確認假設

| 編號 | 假設 | 若不成立 |
|---|---|---|
| A-01 | 使用者接受「預測週期固定為 5/10/20，不可自訂」 | 需改為前端可選，參數校驗與快取鍵都要改 |
| A-02 | 三檔週期足以覆蓋使用情境 | 需擴充至 1／60 日，樣本效率下降 |
| A-03 | 「收盤價」是唯一需要的預測對象 | 若需預測日內高低，模型須改為多輸出 |
| A-04 | `buyZone.target` 可作為 `p_target` 的標的價位 | 若需獨立目標價，須另立參數 |

### 3.7 相依項目

- **依賴 GAP-2 修復**（復權），否則 AC-04 在除權標的上必然失敗。
- 依賴 §4 的預測模型選型。
- 依賴 §10.2 的批次端點（AS 需要跨標的呼叫）。

## 4. FP-2 輸入資料

### 4.0 六要素速查

| 要素 | 內容 | 詳見 |
|---|---|---|

### 4.1 資料來源

| 來源 | 用途 | 必要欄位 | 現況 |
|---|---|---|---|
| Yahoo Finance chart API | 主來源，日線 | `timestamp, open, high, low, close, volume` ＋ **`adjclose`** | 已接，但 adjclose 未取用（GAP-2） |
| 東方財富 | 備援 | 同上 | 已接 |
| 騰訊行情 | 最後備援 | 同上（無 adjclose） | 已接，**需在規格中標明復權能力差異** |

> **復權處理規格**：以 `adjclose / close` 得每日調整因子，回溯調整 `o/h/l`。若來源無 `adjclose`（騰訊），**不得**靜默使用原始價，須在 `pred.quality.adj` 標為 `"none"`，且該標的**不進入 AS 排序前 10 名**（見 §10.7）。

### 4.2 必要欄位與時間範圍

| 欄位 | 必要性 | 缺失時 |
|---|---|---|
| `t`（時間戳） | 必要 | 該根剔除 |
| `c`（收盤） | 必要 | 該根剔除 |
| `o, h, l` | 必要（模型用） | 用 `c` 補，並記 `filled: ["o","h","l"]` |
| `v`（成交量） | 選用（僅品質加權用） | 記 `filled:["v"]`，不影響預測 |
| `adjclose` | **必要（復權用）** | 見 §4.1，降級並標記 |

- 時間範圍：**至少 250 根、最多 500 根**交易日。
- 週線資料**不參與** FP（週線僅 5 年 ≈ 260 根，與日線資訊重疊且對齊困難）。

### 4.3 前置處理步驟（順序固定，不可調換）

1. **剔除無效根**：`c` 為 `null`／`<= 0` 者移除（沿用現行 `chart()` 的 `if (c == null) continue`）。
2. **復權調整**：套用 `adjclose / close` 因子（見 §4.1）。
3. **缺值補齊**：`o/h/l` 缺則以 `c` 補。
4. **異常根標記**（非移除）：單日 `|ln(c_t/c_{t-1})| > 0.35`（≈ ±42%）標為 `outlier`，**保留但加權降低**（見 §6.2）。
5. **交易日連續性檢查**：相鄰兩根間隔 > 10 個日曆日 → 標為 `gap`（長假或停牌），該處**不切分**但記入 `quality.gaps`。
6. **視窗對齊**：取**最後** `lookback` 根（不是最前），確保預測原點是今日。

### 4.4 資料不足或欄位缺失的替代作法

| 缺失程度 | 替代作法 | 對外表現 |
|---|---|---|
| 無日線資料 | 直接回 `status:"unavailable"` | 「查無此標的的行情資料」（沿用現有錯誤文案） |
| 根數 < 250 | 不做預測 | `status:"insufficient"`，顯示還缺幾根 |
| 有 250–499 根 | 用實際根數計算 | `quality:"low"`，UI 加註「樣本偏少」 |
| 無 `adjclose`（騰訊來源） | 用原始價，標記 `adj:"none"` | UI 加註「未復權，除權日附近數字可能失真」 |
| 部分根缺 OHLC | 以收盤補 | 記 `filled`，不影響 UI |
| 全池批次時個別失敗 | 該檔標 `failed`，**不阻斷整個批次** | 見 §10.8 |

## 5. FP-3 回測機制

### 5.0 六要素速查

| 要素 | 內容 | 詳見 |
|---|---|---|
| 功能範圍 | walk-forward 模型回測，驗證預測誤差；**不改寫**既有 `backtest` | §5.1–5.2 |
| 輸入 | 凍結資料快照（`asOfDate` 之前的日線）、`horizons`、`seed`、`dataHash` | §5.2 |
| 輸出 | `pred.validation{n, asOfDate, dataHash, horizons{h:{PICP,MPIW,Brier}}, benchmarks{B0,B1,B2}}` | §5.2 |
| 必要參數 | 驗證期 252 交易日、每週期 ≥60 原點、固定 `seed`、資料須凍結落地 | §5.3 |
| 邊界條件 | 原點 <60→該週期 `insufficient`；資料未凍結→拒絕執行（不可重現） | §5.3 |
| 驗收標準 | AC-11–AC-15（5 項） | §5.6 |
| 待確認假設 | A-08–A-10（3 項） | §5.7 |
| 相依項目 | FP-2 輸出、GAP-4（成本假設）、§13 P2 Go/No-Go 關卡 | §13 |


### 5.1 與既有回測的關係（重要）

> 既有 `backtest()` 是**策略回測**（觸及買區後的績效），本節是**模型回測**（預測誤差的驗證）。兩者**同時存在、互不改寫**。
>
> 命名強制區隔：既有欄位仍為 `backtest`；新增欄位一律置於 `pred.validation` 下，**不得**命名為 `backtest`。

### 5.2 回測流程（可重現）

固定六步，每步輸出可存檔的中間結果：

1. **凍結資料快照**：指定 `asOfDate`（回測截止日），抓取 `asOfDate` 之前的日線。**快照須落地**（JSON 檔或 DB），確保日後重跑結果一致。
2. **建立預測原點清單**：從第 `minSamples+1` 根起，每根都可作為原點（**walk-forward，逐步前進**）。
3. **逐點預測**：對每個原點 `i`，**只用 `candles[0..i]`** 計算 `h=5/10/20` 的預測。**嚴禁**使用 `i` 之後的任何資料（未來函數洩漏）。
4. **比對實際**：取 `candles[i+h].c` 為實際值。
5. **彙總指標**：見 §6。
6. **輸出報告**：`pred.validation` 含 `n`、各週期指標、`asOfDate`、`seed`、`dataHash`。

### 5.3 回測期間與資料切分

| 項目 | 規格 |
|---|---|
| 資料切分 | **Walk-forward（滾動前推），不做隨機切分**。理由：時間序列隨機切分會洩漏未來資訊 |
| 訓練／驗證邊界 | 每個原點皆重新擬合，訓練集 = 該原點之前的全部資料（擴張視窗） |
| 回測期間 | **最近 252 個交易日**（約 1 年）作為驗證區；更早的資料僅作訓練 |
| 最少樣本 | 每個週期至少 **60** 個預測原點，否則該週期標 `insufficient` |
| 重跑一致性 | 同 `asOfDate` + 同 `dataHash` + 同 `seed` → 結果**逐位元相同** |

### 5.4 比較基準（Benchmark）

預測必須**勝過**以下兩個基準才算有效，否則不得對外顯示「有預測能力」：

| 基準 | 定義 | 為什麼要有 |
|---|---|---|
| **B0 隨機漫步** | 預測值 = 今日收盤（即假設未來不變） | 最笨的基準；打不過它代表模型無資訊量 |
| **B1 歷史分位** | 用過去 252 日的 h 日報酬經驗分位當預測區間 | 純統計基準，無模型 |
| **B2 既有 `probUp20`** | 現有機率欄位 | 確保新模型**至少不比舊的差** |

### 5.5 判定準度是否達標的規則

**採用「雙重門檻」，兩者必須同時滿足**：

| 指標 | 門檻 | 說明 |
|---|---|---|
| 區間覆蓋率 | `[q10,q90]` 的實際命中率落在 **80% ± 5%**（即 75%–85%） | 宣稱 80% 區間就要有 80% 命中；低於 75% 是「過度自信」，高於 85% 是「區間過寬、無用」 |
| 方向準確率 | `p_up` 的 Brier Score **優於 B0 至少 2%** | Brier = `mean((p_up − 實際方向)^2)`。只比 B0 好 2% 以上才算有資訊量 |

**未達標的處理**：
- 單一標的未達標 → 該標的 `pred.status = "unvalidated"`，UI 顯示「此標的預測未通過驗證，僅供參考」，且**排除在 AS 排序外**。
- 全池未達標 → FP 整體功能**不得上線**（視為模型不成立）。

### 5.6 驗收標準

| 編號 | 標準 |
|---|---|
| AC-11 | 對 AAPL `asOfDate=2026-11-25` 連跑兩次，`pred.validation` 的 JSON **深度相等** |
| AC-12 | 刻意在 `candles[i+1..]` 植入極端值，回測結果**不變**（證明無未來函數洩漏） |
| AC-13 | `h=20` 的預測原點數 ≥ 60（252 − 20 − 訓練期） |
| AC-14 | 報告中 `benchmarks` 三項（B0/B1/B2）皆存在且有數值 |
| AC-15 | 對「已驗證通過」與「未通過」各取一檔，`status` 正確分別為 `ok` / `unvalidated` |

| 編號 | 假設 |
|---|---|

## 6. FP-4 準確度評估

### 6.0 六要素速查

| 要素 | 內容 | 詳見 |

| 輸出 | 對外 `PICP/MPIW/Brier`；僅內部 `MAE/RMSE/Directional Accuracy` | §6.1 |
| 必要參數 | PICP 75–85%、MPIW 上限 8/12/18%、Brier ≤0.25、滾動視窗 60 交易日 | §6.2 |
| 邊界條件 | 連續 5 日 PICP<70% 或 >90%→告警；告警後該標的 `degraded` | §6.3 |
| 驗收標準 | AC-16–AC-19（4 項） | §6.4 |

| 相依項目 | FP-3 的 validation 結果、§9.2 排程、Telegram 通道 | §12.2 |


### 6.1 離線評估指標（回測時計算）

| 指標 | 定義 | 用途 |
|---|---|---|
| **PICP**（區間覆蓋率） | 實際值落在 `[q10,q90]` 的比例 | 主指標，見 §5.5 |
| **MPIW**（平均區間寬度） | `mean(q90 − q10) / 今日收盤` | 懲罰「用超寬區間刷覆蓋率」的行為。**必須與 PICP 同時看** |
| **Pinball Loss**（分位損失） | 標準分位數損失，對 q10/q50/q90 分別計算後平均 | 分位預測的標準評分，越低越好 |
| **Brier Score** | `mean((p_up − 實際)^2)` | 方向機率校準度 |
| **Directional Accuracy** | 方向猜對的比例（不計幅度） | 直觀但易被少數大波動掩蓋，僅作輔助 |
| **MAE / RMSE** | 對 `q50`（中位預測）計算 | 點預測誤差 |

> **強制規則**：對外只呈現 **PICP、MPIW、Brier** 三項。MAE／RMSE／Directional Accuracy 僅內部記錄，因為點預測誤差在金融時間序列上**不具可解釋性**（會被波動率主導）。

### 6.2 可接受的誤差門檻

| 週期 | PICP 目標 | MPIW 上限 | Brier 上限 |
|---|---|---|---|
| h=5 | 75%–85% | ≤ 8% of price | ≤ 0.25 |
| h=10 | 75%–85% | ≤ 12% of price | ≤ 0.25 |
| h=20 | 75%–85% | ≤ 18% of price | ≤ 0.25 |

MPIW 上限依 ATR% 縮放：`上限 = min(表中值, 4 × ATR% × √h)`。理由：高波動標的的區間本來就該寬，但不能寬到無意義。

### 6.3 上線後持續監測

**這是全新機制，現有系統完全沒有**（無持久化、無排程）。

| 項目 | 規格 |
|---|---|
| 落地內容 | 每個交易日為每檔產生 `{symbol, asOf, horizons:{h:{q10,q50,q90,p_up,price}}}`, 存為 JSONL 或 DB 表 |
| 落地位置 | 新增 `data/predictions/YYYY-MM-DD.jsonl`（**首選**，零依賴）或既有 DB（若業主提供） |
| 對照時機 | 每個週期到期日（T+5/T+10/T+20）回填實際收盤，計算該筆的 PICP／Brier |
| 滾動監測視窗 | 最近 **60 個交易日**的滾動 PICP／Brier |
| 告警門檻 | 滾動 PICP 連續 **5 個交易日** < 70% 或 > 90% → 觸發告警（沿用 `lib/telegram.js`，見 §10.9） |
| 降級規則 | 告警觸發後，該標的 `status` 降至 `degraded`，UI 顯示「近期預測失準」 |
| 人工複核 | 每 **20 個交易日**輸出一份監測報告（PICP／MPIW／Brier 趨勢） |

## 7. FP-5 異常與缺資料處理

### 7.0 六要素速查

| 要素 | 內容 | 詳見 |
|---|---|---|
| 功能範圍 | 七類異常偵測 ＋ 五級回退（R1–R5），禁止靜默失敗 | §7.1、§7.3 |
| 輸入 | 原始 candles ＋ 當前時間（判斷延遲用） | §7.1 |
| 輸出 | `quality` 標記、`status` 五態、對應 UI 文案 | §7.2–7.3 |
| 必要參數 | 價格異常 `abs(ln) > 0.35`、量異常 `20×median`、停滯 `5 根 h==l`、延遲 `4 小時`、斷裂 `3 根` | §7.1 |
| 邊界條件 | 連續缺漏 >3 根→`insufficient`；outlier 佔比 >10%→`quality:"low"` | §7.2 |
| 驗收標準 | AC-20–AC-23（4 項） | §7.4 |
| 待確認假設 | A-14–A-16（3 項） | §7.5 |
| 相依項目 | FP-2 前置處理、FP-6 UI 呈現、既有 `advancedTools` 容錯先例 | §12.2 |


### 7.1 偵測規則（全部具體化）

| 類型 | 偵測條件 | 判定 |
|---|---|---|
| **缺漏** | `c` 為 `null`／`<=0` | 剔除該根 |
| **缺漏（整段）** | 相鄰兩根間隔 > 10 日曆日 | 標 `gap`，不剔除 |
| **延遲** | `now − lastBar.t` > (市場收盤後 4 小時)。交易日 4 小時後仍無當日 K 線 | 標 `delayed`，**沿用前一根**，`stale:true` |
| **異常值（價格）** | `abs(ln(c_t / c_{t-1})) > 0.35` | 標 `outlier`，權重降為 0.3（不剔除，因除權可能被誤判） |
| **異常值（量）** | `v_t > 20 × median(v, 前一月)` | 標 `vol_spike`，不影響價格預測 |
| **異常值（停滯）** | 連續 ≥ 5 根 `h == l`（一字板／停牌） | 標 `frozen`，該段不作為預測原點 |
| **資料不足** | 有效根數 < 250 | `insufficient` |

### 7.2 處理策略

| 情境 | 策略 |
|---|---|
| 單根缺漏 | 剔除後**重新對齊**，不補值（補值會製造假資料） |
| 連續缺漏 ≤ 3 根 | 剔除，並在 `quality.gaps` 記錄 |
| 連續缺漏 > 3 根 | 該標的 `insufficient`（資料鏈斷裂，模型不可信） |
| 延遲 | 用前一根收盤當預測原點，`asOf` 標為該根日期（**不是今日**），UI 明示 |
| 異常值 | 保留但降權；若同一標的 `outlier` 佔比 > 10%，降級為 `quality:"low"` |

### 7.3 預測無法產生時的回退行為

依嚴重度分五級，**每一級都有明確 UI 表現**，禁止靜默失敗：

| 等級 | 觸發 | 回退行為 | UI 表現 |
|---|---|---|---|

### 10.3 資料流

```
使用者查詢
  → /api/analyze?symbol=X
    → datasource.chart(X,'2y','1d')        [既有，加復權]
    → analyzer.analyze()                    [既有，欄位不改]
      → buildAdvancedTools()                [既有，不動]
      → predict(X, candles)                 [新增，try/catch 包住]
    → 回傳 { ...既有16欄, pred:{...} }
  → 前端 renderPred(data.pred)              [新增]

每日批次（排程）
  → /api/pred/batch
    → 對 154 檔逐一呼叫 predict()（併發上限 4）
    → 排序、篩選（見 §11.5）
    → 落地 data/predictions/YYYY-MM-DD.jsonl
    → 供首頁 #aiPicks 讀取
```

### 10.4 效能考量（實測基線）

| 項目 | 實測／規格 | 說明 |
|---|---|---|
| 單次 analyze 現況 | AAPL **576ms** / 56KB；0700.HK **435ms** / 46KB | 含 4 個進階模組 |
| FP 單檔增量預算 | **≤ +300ms** | 若超過，須改為非同步（先回既有欄位，`pred` 以 SSE／輪詢補） |
| analyze 回應包體上限 | **≤ 70KB** | 現 56KB + `pred` 約 4KB，餘裕充足 |
| 批次 154 檔 | 併發 4，單檔 600ms → **約 24 秒** | 可接受；若超過 60 秒須改為分批落地 |
| 批次記憶體 | 154 × 60KB ≈ **9MB** 峰值 | 若全量保留，需流式處理（逐檔寫入後釋放） |
| 首批載入（首頁選股） | 讀落地檔，**≤ 100ms** | 不即時計算，直接讀檔 |

**前端效能**：
- 預測卡片渲染必須 **≤ 16ms**（一個 frame），不得觸發 layout thrashing。
- 區間條用 SVG 或 canvas，**不可**用 154 個 DOM 節點堆疊。

### 10.5 標的池定義（AS 的必要前提）

| 項目 | 規格 |
|---|---|
| 池來源 | 本地別名索引 `lib/alias.js` 的 `ZH` + `EN` 去重 → **154 檔**（實測） |
| 為何不用全市場 | 全市場（美股 ~8000 + 港股 ~2600）每檔 600ms → 超過 1 小時，且上游會限流（現有熔斷機制會被打爆） |
| 池擴充方式 | 手動新增 `lib/alias.js`，**不改程式** |
| 流動性過濾 | 20 日均量 < **100,000 股** 者排除（避免無法成交） |
| 價格過濾 | 收盤 < **1.0**（當地幣別）者排除（低價股噪音大） |
| 排除標的 | `quality.adj == "none"`、`status != "ok"`、`pred.status == "unvalidated"` |

> **待確認 A-23**：154 檔是否足夠覆蓋使用者的關注範圍。若需擴充至 500 檔，批次時間將增至約 78 秒，且需評估上游限流。

### 10.6 首頁整合（第 9 項要求）

**現況衝突**：`#welcome` 是靜態歡迎卡，`public/app.js` 有 4 處切換它的 `hidden`。AS 清單**不可**放在 `#welcome` 內部（會被查詢後隱藏）。

### 11.1 功能範圍

| 項目 | 規格 |
|---|---|
| 目的 | 每交易日產出「可買入」的股票清單，顯示於首頁 |
| 標的範圍 | §10.5 定義的 154 檔池（**非全市場**） |
| 候選產生 | **先用 FP + 既有指標算分排序**（本地，零成本），**再由 LLM 做最後排序與理由生成** |
| LLM 角色 | **只做排序與解釋，不做選股**。避免 LLM 幻覺引入不存在的標的 |
| 輸出數量 | 每日 **3–10 檔**（少於 3 檔視為「今日無適合標的」，多於 10 檔截斷） |
| 不包含 | 不產生買賣建議、不預測具體進出場價位（那是 `buyZone` 的職責） |

### 11.2 為什麼要「本地先篩，LLM 後排」

若直接把 154 檔丟給 LLM 選股，會有三個問題：
1. **成本**：154 檔的完整資料遠超單次 context，需分批呼叫，成本 × N。
2. **幻覺**：LLM 可能推薦不存在的代碼或編造理由。
3. **不可重現**：LLM 輸出非確定性，無法回測。

因此分工為：**本地計算客觀分數（可重現、可回測）→ LLM 只做前 20 名的重排與文字解釋**。

### 11.3 API 輸入規格

**呼叫對象**：任一 OpenAI 相容 `/chat/completions` 端點（可設定 base URL，故 OpenAI／DeepSeek／Moonshot 皆可）。

**環境變數**：
```
AI_API_BASE=https://api.openai.com/v1
AI_API_KEY=sk-...
AI_MODEL=gpt-4o-mini
AI_TIMEOUT_MS=25000
```

**請求內容**（結構化，非自然語言）：

```json
{
  "model": "gpt-4o-mini",
  "temperature": 0.2,
  "response_format": { "type": "json_object" },
  "messages": [
    { "role": "system", "content": "<固定系統提示，見附錄 A>" },
    { "role": "user", "content": "<候選清單 JSON，見下>" }
  ]
}
```

**`user` content 的結構**（本地先算好，LLM 只讀）：

```json
{
  "date": "2026-11-25",
  "candidates": [
    {
      "rank_local": 1,
      "symbol": "AAPL",
      "name": "Apple Inc.",
      "price": 354.07,
      "score": 65.0,
      "verdict": "watch-buy",
      "zone_lower": 331.34, "zone_upper": 337.27,
      "dist_to_zone_pct": -4.82,
      "pred": { "h5": {"q10":343.1,"q50":355.2,"q90":366.5,"p_up":0.58},
                "h10":{"q10":337.2,"q50":356.1,"q90":372.0,"p_up":0.61},
                "h20":{"q10":328.4,"q50":357.3,"q90":381.2,"p_up":0.64} },
      "atr_pct": 2.35,
      "avg_vol20": 58200000
    }
    // …最多 20 筆
  ]
}
```

**強制限制**：單次送入 **≤ 20 檔**，JSON ≤ **8,000 tokens**（約 32KB）。

### 11.4 API 輸出規格

**要求 LLM 回傳**（`response_format: json_object` 強制 JSON）：

```json
{
  "picks": [
    { "symbol": "AAPL", "rank": 1, "reason": "…40 字內…", "risk": "…20 字內…" }
  ]
}
```

**驗證規則（回傳後必做）**：
1. `symbol` **必須**存在於送入的候選清單中，否則**丟棄該筆**（防幻覺）。
2. `picks` 長度 3–10，超出則截斷／視為失敗。
3. `reason` 長度 ≤ 60 中文字，`risk` ≤ 30 中文字，超出則截斷。
4. 任一驗證失敗 → 走 §11.7 回退。

### 11.5 排序與篩選規則

**第一階段：本地客觀分（可回測、可重現）**

| 因子 | 權重 | 計算 |
|---|---|---|
| FP 方向機率（h=10） | **0.40** | `p_up(10)` |
| 距買區距離 | **0.25** | `max(0, 1 − abs(dist_to_zone_pct)/10)`，越接近買區越高 |
| 既有 `score` | **0.20** | `score / 100` |
| 風險調整 | **0.15** | `min(1, 4/atr_pct)`，波動越低越高分 |

- 客觀分 = 加權和，範圍 0–1。
- 取前 **20 名**送入 LLM。
- **硬性過濾**（在算分前執行）：`quality.adj == "none"`、`status != "ok"`、`pred.status == "unvalidated"`、均量 < 100k、價格 < 1.0 → 全部排除。

**第二階段：LLM 重排**

- LLM 可調整順序，但**不得**引入新標的。
- 最終排序 = LLM 給的 `rank`（若 LLM 失效，用本地客觀分排序，見 §11.7）。

**篩選門檻（最終）**：
- 最終清單只保留 `客觀分 ≥ 0.55` 的前 N 檔（N = min(10, 符合數)）。
- 若符合數 < 3 → 顯示「今日無明確機會」（**不硬湊**）。

### 11.6 每日執行時機

| 項目 | 規格 |
|---|---|
| 時機 | 收盤後 30 分鐘（與 §9.2 S1 排程同一觸發點） |
| 順序 | ①FP 批次（154 檔）→ ②本地算分 → ③取前 20 → ④呼叫 LLM → ⑤驗證 → ⑥落地 |
| 總時長預算 | **≤ 90 秒**（批次 24s + 算分 1s + LLM 25s + 餘裕） |
| 落地 | `data/picks/YYYY-MM-DD.json`，含 `picks`、`generatedAt`、`model`、`candidatesCount`、`llmLatencyMs` |
| 讀取 | 首頁讀**當日**檔；無當日檔 → 讀**最近一份**並標示「資料日期：YYYY-MM-DD」 |

### 11.7 無結果或 API 失敗的處理

| 情境 | 處理 | 使用者看到 |
|---|---|---|
| **候選池無任何標的通過硬性過濾** | 不呼叫 LLM | 「今日無符合條件的標的」（附原因統計：N 檔因資料不足排除…） |
| **客觀分 ≥ 0.55 者 < 3 檔** | 不呼叫 LLM | 「今日無明確機會，建議觀望」 |
| **LLM 逾時（>25s）** | **降級：用本地客觀分排序前 5 檔** | 清單正常顯示，卡片標「AI 排序暫不可用，按本地評分排序」 |
| **LLM 回 4xx（金鑰錯／額度滿）** | 同上降級 ＋ 記錄錯誤 | 同上，並在後台 log `AI_API_ERROR` |
| **LLM 回 5xx／網路錯誤** | 同上降級，**重試 1 次**（間隔 3s） | 同上 |
| **LLM 回傳格式不符（非 JSON／缺 picks）** | 同上降級 | 同上 |
| **LLM 回傳含不存在 symbol** | 丟棄該筆；若剩 <3 檔 → 降級 | 同上 |
| **未設 `AI_API_KEY`** | **完全跳過 LLM**，純本地排序 | 卡片標「AI 未設定，按本地評分排序」 |
| **當日完全無資料（排程失敗）** | 讀最近一份；逾 3 天則顯示錯誤 | 「選股資料更新失敗，最近資料：MM-DD」 |

> **核心原則**：**LLM 是加值，不是必要路徑**。任何 LLM 失敗都不得讓首頁空白或報錯。

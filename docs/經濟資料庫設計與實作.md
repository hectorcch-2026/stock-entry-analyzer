## 0. 先講兩件會改變設計的事

### ① 為什麼不用 SQLite

直覺上「經濟資料庫」就該用 SQLite。Node 22.5+ 內建 `node:sqlite`，零依賴，看起來完美。**但本專案的部署環境是 Node 20。**

| 事實 | 來源 |
|---|---|
| Dockerfile 用 `FROM node:20-alpine` | `Dockerfile:5` |
| render.yaml 指定 `NODE_VERSION=20` | `render.yaml` |
| 專案宣告 `engines: node >=18` | `package.json` |
| `node:sqlite` 需要 Node 22.5+ | Node 官方文件；本機 v22.22.2 實測可用 |

若用 `node:sqlite`，**本機（v22）所有測試都會通過，一部署到 Node 20 就 `MODULE_NOT_FOUND`**——這是最糟的一種失敗：本機綠燈、上線炸掉。

另外專案明文 `dependencies: {}`，所以 `better-sqlite3`（需要原生編譯）也不可用。

**結論**：沿用本專案既有的 JSON 落地模式（`lib/screener.js`、`lib/scheduler.js` 都這樣做），但補上它們原本沒有的**原子寫入**與**唯一鍵去重**。

資料量級估算：18 條序列 × 約 1,000 期 ≈ **2 萬列**，JSON 完全夠用（目前 4 筆佔 2 KB）。而且 JSON 可以直接 `cat` 檢查、用 git 比對 diff、用任何工具讀取，除錯成本遠低於二進位資料庫。

### ② 為什麼三個表放在同一個檔

三個邏輯表存在同一個 `state.json`，不是三個檔案。理由是**原子性**：

```
write tmp → rename  ← 這一步是作業系統層級的原子操作
```

一次 `rename` 就能讓三張表同時生效。若拆成三個檔，中途崩潰會留下「值已更新、但修訂紀錄沒寫」的不一致狀態——而修訂紀錄正是這個系統可信度的來源。

## 1. 資料表設計

### 1.1 表① `series` — 指標主檔

**一列 = 一個指標的定義**（不是數值）。唯一鍵 `seriesKey`。

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `seriesKey` | string | ✅ | **主鍵**。程式內使用的短名，如 `cpiYoy` |
| `label` | string | ✅ | 指標名稱，如「CPI 年增率」 |
| `unit` | string | ✅ | 單位，如 `%`、`指數（2017=100）`、`千人` |
| `frequency` | string | ✅ | 統計週期：`D` 日／`W` 週／`M` 月／`Q` 季／`Y` 年 |
| `periodFormat` | string | auto | 由 `frequency` 推導，如月頻為 `YYYY-MM` |
| `source` | string | | 資料來源，如 `FRED`、`TE`、`BLS` |
| `sourceId` | string | | 來源端的原始代碼，如 `CPIAUCSL` |
| `sourceUrl` | string | | 可回溯的原始網址 |
| `definition` | string | | **這個數字在衡量什麼**（給人看，也是防誤用的關鍵） |
| `note` | string | | 使用限制，如「日頻但只在 FOMC 後變動」 |
| `autoCreated` | boolean | | 由寫入自動補的最小主檔（尚未有真定義） |
| `createdAt` / `updatedAt` | ISO string | auto | 建立／最後更新時間 |

> `definition` 與 `note` 不是裝飾。本專案的文件裡記過：同一個「CPI」在不同來源可能是年增率也可能是指數，單位不同、不能相比。把定義寫進資料庫，比寫在文件裡可靠。

### 1.2 表② `observations` — 觀測值

**一列 = 某指標在某期間的值**。唯一鍵 **`(seriesKey, period)`**。

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `id` | string | ✅ | **唯一標識**，格式 `${seriesKey}|${period}`，如 `cpiYoy|2026-10` |
| `seriesKey` | string | ✅ | 外鍵 → `series.seriesKey` |
| `period` | string | ✅ | **正規化後**的期間鍵，如 `2026-10` |
| `value` | number | ✅ | 數值。**不可為 null**（null 代表「沒資料」，不寫入） |
| `unit` | string | | 冗餘存放，避免查詢時還要 join |
| `frequency` | string | | 同上 |
| `source` | string | | 這筆值來自哪個來源 |
| `sourceUpdatedAt` | ISO string | | **來源端**的更新時間（不是本地寫入時間），用於判斷資料新舊 |
| `firstSeenAt` | ISO string | auto | 首次寫入本庫的時間 |
| `updatedAt` | ISO string | auto | 最後一次值變動的時間 |
| `revisionCount` | number | auto | 這筆被修訂過幾次 |

**索引**（邏輯上）：
- `id` 唯一索引 → 去重與定位
- `(seriesKey, period)` 複合唯一索引 → 同上，另一種表達
- `(seriesKey, period)` 排序 → 時間序列查詢

> 實作為 `Map<id, observation>` + `Map<seriesKey, series>`，O(1) 定位；排序在查詢時做（2 萬列排序 < 5ms，可接受）。

### 1.3 表③ `revisions` — 修訂軌跡

**一列 = 一次值變動**。這是「更新」與「覆寫」的差別所在。

| 欄位 | 型別 | 說明 |
|---|---|---|
| `seriesKey` | string | 哪個指標 |
| `period` | string | 哪一期 |
| `prevValue` | number | 改動前的值 |
| `newValue` | number | 改動後的值 |
| `changedAt` | ISO string | 何時改的 |
| `source` | string | 來源 |
| `reason` | string | 預設 `value-changed` |

**為什麼需要這張表**：CPI 會**事後修訂**——同一個期間的數字可能在幾個月後被官方改掉。如果不記錄，你會看到「上個月看是 3.7，這個月看是 3.5」卻說不出為什麼，也無法回溯。

同時保留上限（預設 5,000 筆），超過時丟最舊的並記入 `droppedRevisions`——**不讓它無聲消失**。

## 2. 唯一標識與正規化

### 2.1 唯一標識

```
id = seriesKey + "|" + period
例：cpiYoy|2026-10
```

用管線符號 `|` 是因為它不可能出現在指標名或日期裡。

### 2.2 期間正規化（去重的真正關鍵）

**這一步沒做好，去重就是假的。**

同一個月，不同來源給的日期不一樣：

| 來源 | 可能給的日期 |
|---|---|
| FRED | `2026-10-01` |
| 某來源（月末） | `2026-10-31` |
| 另一來源（發布日） | `2026-10-15` |

若直接拿日期字串當鍵，**同一個月會存成三筆**，圖表就會出現「同月三個點」。

正規化規則：

| 頻率 | 輸出格式 | `2026-10-01` → | `2026-10-31` → |
|---|---|---|---|
| `M` 月 | `YYYY-MM` | `2026-10` | `2026-10` ← 收斂 |
| `D` 日 | `YYYY-MM-DD` | `2026-10-01` | `2026-10-31`（不同期） |
| `Q` 季 | `YYYY-Qn` | `2026-Q4` | `2026-Q4` ← 收斂 |
| `Y` 年 | `YYYY` | `2026` | `2026` ← 收斂 |

**兩個容易漏掉的細節**：

1. **月份必須補零**。`2026-9` 在字串比較中 **大於** `2026-10`（因為 `'9' > '1'`），期間排序會整個亂掉。實測已鎖在測試 `A2`。
2. **日頻缺日不可猜成月初**。`2026-10` 傳給日頻要回 `null` 並跳過，否則兩筆不同的日資料會撞成同一個鍵。

解析刻意**不用 `new Date()`**——`new Date('2026-10-01')` 在不同環境會被當成 UTC 或本地時間，跨時區會位移一天。手動用正則取年月日才可預測。

## 3. 更新邏輯（本設計的核心）

### 3.1 一句話：不是「有就覆寫」，而是逐項判斷

需求問的是「資料已存在時應如何更新」。這裡有**六種**情況，一律用同一個函式 `decide()` 判斷：

| # | 情況 | 動作 | 理由 |
|---|---|---|---|
| 1 | 沒有既有紀錄 | `insert` | 新資料 |
| 2 | 新值為 `null` / 非數值 | **`skip`** | `null` 是「沒資料」，不是 0。用它蓋掉真值會讓圖表出現假缺口 |
| 3 | 值完全相同 | **`unchanged`** | 不寫檔、不記修訂。**這就是「避免重複抓取」的效果** |
| 4 | 來源更新時間比既有的**更舊** | **`skip` (stale)** | 遲到的舊回應不可覆蓋新資料 |
| 5 | 值不同，來源時間較新 | `update` + 記修訂 | 正常更新 |
| 6 | 值不同，但沒有來源時間可比較 | `update` + 記修訂 | 保守：以值為準，不可因此漏更新 |

### 3.2 為什麼第 2 條最重要

如果 `null` 可以覆蓋真值：

```
10 月 CPI 抓到 3.72    → 寫入
下次抓取上游故障回 null → 覆蓋成 null
```

結果是**資料在沒有任何錯誤訊息的情況下消失**。這比抓取失敗更糟，因為它看起來「成功」了。

所以規則寫死：**`null` 永遠不寫入，也永遠不覆蓋**。若某期真的沒有資料，就是「沒有這一列」，而不是「有一列值是 null」。查詢時自然查不到，前端才能正確區分「沒資料」與「值為 0」。

### 3.3 為什麼第 4 條需要存在

真實情境：兩個請求間隔發出，較早的請求因為重試而較晚回應。

```
T1: 請求 A（來源時間 11-10）發出
T2: 請求 B（來源時間 11-20）發出並回應 → 寫入 11-20 的值
T3: 請求 A 奾奾回應（較舊）→ 若無保護，會把新值蓋回舊值
```

這種 bug **只會偶發一次**，重現極難，但會讓數值退回上一期。用 `sourceUpdatedAt` 字串比較即可擋掉（ISO 格式下字典序 = 時間序）。

### 3.4 批次寫入的報表

每次寫入都回傳一份統計，這份報表就是「有沒有重複寫入」的證據：

```json
{
  "received": 3, "inserted": 3, "updated": 0, "unchanged": 0,
  "skipped": [], "errors": [], "revisions": 0,
  "duplicatesInBatch": 0,
  "ids": ["cpiYoy|2026-08", "cpiYoy|2026-09", "cpiYoy|2026-10"]
}
```

同一批再送一次：

```json
{ "received": 3, "inserted": 0, "updated": 0, "unchanged": 3 }
```

`inserted: 0` 且 `unchanged: 3` 就是「沒有重複寫入」的直接證據。

## 4. 寫入、查詢、更新 — 三個 API

### 4.1 寫入（upsert）

```http
POST /api/econ/observations
Content-Type: application/json

{ "rows": [
  { "seriesKey": "cpiYoy", "period": "2026-10-01", "value": 3.55, "source": "FRED" }
] }
```

也可只傳單筆（不包 `rows`）：`{ "seriesKey": "...", "period": "...", "value": ... }`

### 4.2 查詢

```http
GET /api/econ/query?series=cpiYoy&from=2026-01&to=2026-10&order=desc&limit=12
```

| 參數 | 說明 |
|---|---|
| `series` | 指標 key；不給則查全部 |
| `from` / `to` | 期間範圍（含端點） |
| `order` | `asc`（預設）／`desc` |
| `limit` | 取幾筆，搭配 `desc` 可拿最新 N 筆 |

**錯誤處理刻意區分兩種 404**：

| 情況 | 回應 |
|---|---|
| 資料庫沒有這個指標 | `404 UNKNOWN_SERIES` + 提示先 sync |
| 有指標但該期間沒資料 | `200` + `count: 0` |

這兩件事不能混。使用者需要知道是「我打錯指標名」還是「這期還沒發布」。

### 4.3 更新

```http
PATCH /api/econ/observations
{ "seriesKey": "cpiYoy", "period": "2026-10-01", "value": 3.48 }
```

**更新找不到 → `404 NOT_FOUND`，不自動新增。** 更新與寫入的語義必須分開，否則打錯一個字母就會憑空長出一筆資料。

## 5. 持久化

### 5.1 原子寫入

```js
fs.writeFileSync(tmp, JSON.stringify(state));  // 先寫暫存
fs.renameSync(tmp, file);                       // 再一次替換
```

直接 `writeFile` 到目標檔的話，寫到一半斷電會留下半個 JSON，**下次啟動整庫解析失敗**。`rename` 在同一檔案系統上是原子操作。

> 已在 Windows 實測 `renameSync` 覆蓋既有檔可行，並有測試 `D4` 確認不留下 `.tmp` 殘檔。

### 5.2 檔案損壞的處理

若 `state.json` 解析失敗，**不覆蓋**，而是改名為 `state.json.corrupt-{timestamp}` 後以空庫啟動。使用者資料不可以因為一次讀取失敗就消失。此行為有測試 `H1` 鎖住。

### 5.3 版本不符

若檔案 `schemaVersion` 與程式不符，**直接拋錯**，不嘗試解讀。默默誤讀比明確報錯危險得多。

## 6. 避免重複抓取（需求的關鍵要求）

有三層防護，從便宜到貴：

| 層 | 機制 | 省下什麼 |
|---|---|---|
| ① 期間比對 | `(seriesKey, period)` 已存在且值相同 → `unchanged` | 不寫檔、不記修訂 |
| ② 新鮮度檢查 | `needsRefresh()` 依頻率判斷 TTL | **完全不發上游請求** |
| ③ 上游快取 | `lib/macro.js` 的記憶體 TTL Map | 同一秒內重複呼叫 |

### 6.1 新鮮度依頻率，不寫死秒數

| 頻率 | TTL | 理由 |
|---|---|---|
| 日頻 | 6 小時 | 收盤前根本不會變，5 分鐘抓一次純浪費 |
| 月頻 | 24 小時 | 一個月才變一次 |
| 季頻 | 30 天 | 同上 |

### 6.2 實測效果

```http
POST /api/econ/sync  { "keys": ["cpiYoy", "unrate"] }
```

第一次（本地無資料）→ 真的去抓。第二次（剛抓過）：

```json
{
  "synced": false,
  "message": "所有序列的本地資料都還新鮮，未向上游發出任何請求",
  "skippedFresh": [
    { "key": "cpiYoy", "reason": "fresh" },
    { "key": "unrate", "reason": "fresh" }
  ]
}
```

**「未向上游發出任何請求」是這句話的字面意思**——連一次 HTTP 都沒發。

## 8. 已知限制（誠實列出）

| 限制 | 說明 | 影響 |
|---|---|---|
| **浮點嚴格相等** | `3.72` 與 `3.7200000001` 會被視為不同值，記一次假修訂 | 同一上游同一格式不會發生；若自行計算比率需改容差比較（測試 `C9` 已註記） |
| **全量重寫** | 每次存檔重寫整個 JSON | 2 萬列約 2 MB，寫檔 < 50ms 可接受；超過 10 萬列應改 SQLite |
| **單進程** | 無檔案鎖，兩個進程同時寫同一檔會互相覆蓋 | 本專案為單進程服務，符合現況；多進程需改用資料庫 |
| **無交易日曆** | 只存有資料的期間，不補「應該有但沒有」的期間 | 前端需自行判斷缺口，不可假設期間連續 |
| **同步只取最新一期** | `fred.getSeries` 只回最新值＋統計，不含完整歷史 | 要回補整條歷史需另接 `fred.fetchSeries`（store 的 `writeMany` 已支援批次） |
| **`node:sqlite` 未使用** | 因部署為 Node 20 | 若日後升到 Node 22+，可考慮遷移（schema 已對應） |

## 9. 若日後要遷移到 SQLite

schema 已刻意設計成可直接對應：

```sql
CREATE TABLE series (
  series_key    TEXT PRIMARY KEY,
  label         TEXT NOT NULL,
  unit          TEXT NOT NULL DEFAULT '',
  frequency     TEXT NOT NULL CHECK (frequency IN ('D','W','M','Q','Y')),
  period_format TEXT,
  source        TEXT,
  source_id     TEXT,
  source_url    TEXT,
  definition    TEXT,
  note          TEXT,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

CREATE TABLE observations (
  id                 TEXT PRIMARY KEY,          -- seriesKey|period
  series_key         TEXT NOT NULL REFERENCES series(series_key),
  period             TEXT NOT NULL,
  value              REAL NOT NULL,             -- NOT NULL 就是「null 不入庫」的資料庫層保證
  unit               TEXT,
  frequency          TEXT,
  source             TEXT,
  source_updated_at  TEXT,
  first_seen_at      TEXT NOT NULL,
  updated_at         TEXT NOT NULL,
  revision_count     INTEGER NOT NULL DEFAULT 0,
  UNIQUE (series_key, period)                   -- 唯一鍵
);

CREATE INDEX idx_obs_series_period ON observations(series_key, period);

CREATE TABLE revisions (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  series_key  TEXT NOT NULL,
  period      TEXT NOT NULL,
  prev_value  REAL NOT NULL,
  new_value   REAL NOT NULL,
  changed_at  TEXT NOT NULL,
  source      TEXT,
  reason      TEXT
);
```

遷移只需把 `writeMany` 裡的陣列操作換成 `INSERT ... ON CONFLICT DO UPDATE`，
上游用同樣的 `decide()` 判斷要不要執行——**決策邏輯與儲存後端是分開的**，這是刻意的。

# 版塊輪動選股流程 — 設計規格

> 目的：把現有的「RRG 版塊輪動」與「個股篩選器」接成一條有因果關係的三階段漏斗，
> 使選股結果帶有「為什麼是這個版塊、為什麼是這檔股票」的可追溯依據。

---

## 0. 一頁總覽

```
┌─ 階段一：版塊輪動（11 → N 個優勢版塊）────────────────────┐
│  輸入：11 個 SPDR 版塊 ETF + SPY 基準（週線）              │
│  計算：RS-Ratio / RS-Momentum → 四象限 + 強弱分數 + 動能方向 │
│  輸出：優勢版塊集（預設前 2 名，約 159 檔成分股）            │
└────────────────────────────────────────────────────────┘
                          ↓ 版塊 → 個股歸屬對照（100% 覆蓋）
┌─ 階段二：建立本次標的池（500 → 約 159）─────────────────┐
│  輸入：S&P 500 母體（500 檔，已排除中概股）+ 版塊持股檔      │
│  條件：① 在母體 ② 有版塊歸屬 ③ 所屬版塊為優勢版塊           │
│  輸出：動態標的池 + 剔除清單（依原因分類）                  │
└────────────────────────────────────────────────────────┘
                          ↓ 逐檔分析
┌─ 階段三：個股選股（約 159 → 前 K 檔）───────────────────┐
│  輸入：動態標的池                                         │
│  條件：技術評分 / 距買區 / 價格 / 波動（沿用現有參數）       │
│  排序：版塊優先 → 個股評分 → 距買區 → 盈虧比               │
│  輸出：候選清單 + 每檔的版塊順風說明                        │
└────────────────────────────────────────────────────────┘
```

**核心設計原則：版塊是「閘門（gate）」，不是「加分項」。**

這一點必須先講清楚，因為兩種做法差很多：

| 做法 | 問題 |
|---|---|
| 版塊強弱當成個股評分的一個加分項 | 分數被兩套尺度混在一起（版塊 strengthScore 0–100 是**同儕百分位**，個股 score 0–100 是**技術面絕對分**）。加權後的數字無法解釋，也無法回測 |
| **版塊作為硬性前提（本設計）** | 只有「版塊對」的股票才會進入候選。理由單純、可稽核：「逆風版塊裡的強勢股，勝率結構性較差」 |

## 1. 階段一：版塊優勢評估

### 1.1 資料來源與欄位

| 項目 | 內容 |
|---|---|
| 版塊代理 | 11 個 SPDR 產業 ETF（`lib/rrg.js` → `SECTORS`）：XLK、XLF、XLV、XLY、XLP、XLE、XLI、XLB、XLRE、XLU、XLC |
| 基準 | 預設 `SPY`（可選 `RSP`／`QQQ`／`IWM`／`DIA`） |
| 週期 | 預設 `weekly`（週線），週期參數 `period=14` |
| 觀察區間 | 預設 `1y`（52 週）；尾跡 5 點 |
| 價格 | **復權價**（`adjclose`）。用未復權價會被股息率扭曲相對強弱 |
| 來源模組 | `lib/rrg-service.js` → `getMatrix()`；`lib/rrg.js` → `buildRRG()` |

> 為什麼用 ETF 當版塊代理，而不是自編成分股等權指數：ETF 是真實可交易報價、
> 成分與權重由指數公司維護（不必自行維護一份會腐壞的清單）、且有成交量。
> 代價是費用率與折溢價，但 RRG 看的是**相對強弱的形狀**，此偏差不影響輪動判讀。

### 1.2 計算指標（逐層推導）

**第 1 層 — 相對強度原始序列**

```
RS[i] = close_sector[i] / close_benchmark[i]
```

**第 2 層 — RS-Ratio（相對強度「水位」）**

```
rsSm    = DEMA(RS, period)          // 雙重指數平滑，降低單週噪音
ratio   = indexTo100(rsSm, period)  // 以 100 為中性重新縮放
```

`ratio > 100` ⇔ 該版塊跑贏基準。這是**位置**。

**第 3 層 — RS-Momentum（相對強度「變化」）**

```
ratioSm  = DEMA(ratio, period)
momentum = indexTo100(ratioSm, period)
```

`momentum > 100` ⇔ 相對強度正在**增強**。這是**速度**。

**第 4 層 — 四象限（`classifyQuadrant`）**

| ratio | momentum | 象限 | 含義 |
|---|---|---|---|
| ≥100 | ≥100 | `leading` 領先 | 強且更強 —— 主升段 |
| ≥100 | <100 | `weakening` 弱化 | 強但轉弱 —— 派發風險 |
| <100 | <100 | `lagging` 落後 | 弱且更弱 —— 迴避 |
| <100 | ≥100 | `improving` 改善 | 弱但轉強 —— 佈局期 |

RRG 的正常輪動是**順時針**：領先 → 弱化 → 落後 → 改善 → 領先。

**第 5 層 — 版塊強弱分數（`lib/sector-macro-ai.js` → `rankSectors`）**

```
rPct      = 該版塊 ratio    在 11 個版塊中的百分位
mPct      = 該版塊 momentum 在 11 個版塊中的百分位
strengthScore = 0.6 × rPct + 0.4 × mPct        // 0–100
```

權重 6:4 的理由（沿用既有實作）：輪動研判中「現在的位置」比「即將的變化」更可靠，
因為動能可以很快反轉，而位置要扭轉需要更長時間。

⚠️ **重要語義**：`strengthScore` 是**同儕百分位**，不是絕對強度。
11 個版塊必然有高有低——第 1 名不代表「很強」，只代表「比其他 10 個強」。
跨期比較請看 `ratio` 的絕對值。

**第 6 層 — 動能方向與翻轉偵測（`analysis` / `cross`）**

| 欄位 | 來源 | 用途 |
|---|---|---|
| `analysis.length` | 尾跡位移量 | 動能是否真的在推進（太短＝盤整） |
| `analysis.angleDeg` | 首→尾方位角 | 移動方向 |
| `analysis.curvature` | 弦弓量（有號） | **負＝順時針（正常輪動）；正＝逆時針（動能鬆動）** |
| `analysis.efficiency` | 直線距離 ÷ 路徑長度 | 接近 1＝單向推進；偏低＝來回震盪 |
| `analysis.signal` | flat / moving / fast | 移動速度分類 |
| `cross.next` | 下一個象限 | 只回報相鄰象限（不可能從領先跳到落後） |
| `cross.confidence` | high / medium / low | 距邊界 <1.0 且朝邊界移動＝high；<2.5＝medium |

### 1.3 版塊納入判定（三類，不是二分）

```
輸入：ranked[]（11 個版塊，已按 strengthScore 排序，含 rank / quadrant / cross）

優勢版塊（FAVORED）— 進入階段二
    條件：quadrant ∈ {leading, improving}
    排序：strengthScore DESC，取前 N（預設 N=2，可調 1–6）
    例外：若 cross.confidence === 'high' 且 cross.next === 'weakening'
          → 降級為「觀察」（即將弱化，不該在此刻加碼）

儲備版塊（WATCH）— 不進池，但列出來
    條件：quadrant === 'weakening' 但 cross.next !== 'lagging'（尚未跌向落後）
       或 quadrant === 'lagging' 但 cross.confidence === 'high' 且 cross.next === 'improving'
    用途：讓使用者看到「下一批可能在轉強的版塊」，而不是只能看當下

迴避版塊（AVOID）
    條件：quadrant === 'lagging'，或 weakening 且 cross.next === 'lagging'
```

**為什麼 FAVORED 不只用「前 N 名」而要先篩象限：**
若 11 個版塊中有 8 個都在 `leading`（實測會發生，因為 ratio 的 100 是固定線而排名是相對的），
「前 N 名」可能全部落在 `weakening`——那時按名次取前 N 會選到正在轉弱的版塊。
先篩象限、再按分數排序，才不會出現這種邏輯矛盾。

> **已定案：預設 N = 2。**
> 成本隨版塊數線性成長（`analyzer.analyze()` 每檔打 3 個上游請求，無法迴避）。
> 前 2 名約 159 檔 → 477 個請求，可在 90 秒預算內完整跑完；
> 前 3 名約 235 檔 → 705 個請求，逼近甚至超出預算。
> 需要更廣覆蓋時可用 `sectorTopN=3~6` 調高，但應同時提高 `SCREEN_BUDGET_MS`。
>
> 這個選擇也解釋了**為什麼「合格數」與「取用數」必須分開顯示**：
> 實測常見 6 個版塊同時位於 leading，但只取前 2 個。
> 若把 6 個都標成「優勢」，畫面上的綠色版塊數就會與漏斗的池內檔數矛盾。
> 因此表 A 的判定欄區分「優勢・已取」與「優勢・未取」兩種。

**為什麼「觀察」類要單獨列出：**
`improving`（左上）是佈局期，`leading`（右上）是主升段。兩者都值得進池，
但使用者的風險偏好不同。把 `weakening` 且尚未崩的版塊列為「觀察」，
等於提供「下一輪的名單」，這是輪動策略真正的價值所在。

## 2. 階段二：建立動態標的池

### 2.1 版塊 ↔ 個股對應關係（這段是全流程的關鍵耦合）

| 項目 | 內容 |
|---|---|
| 資料來源 | `lib/sector-holdings.js` → `getSectorIndex()`，讀**發行商 SSGA 官方每日持股檔**（11 個 ETF 各前 50 大持股） |
| 為什麼不用 Yahoo | Yahoo 的 `topHoldings` 模組已於 2026 年移除：請求回 HTTP 200 但**沒有這個 key**。照文件寫會拿到「200 但空結果」，且看不出原因 |
| 對應結構 | `Map<symbol, [{sector, weight, rank, asOf}]>`，同一檔可能出現在多個 ETF |
| 主場判定 | 取 `weight` 最高者為「主場版塊」（已實作：`list.sort((a,b)=>b.weight-a.weight)` 後取 `[0]`） |
| 次要歸屬 | `candidates` 保留全部，供「跨版塊」說明 |
| 代碼正規化 | `BRK.B → BRK-B`（S&P 寫法 → Yahoo 寫法）。**僅轉換「字母.字母」，不動 `.HK`** |
| 快取 | TTL 6 小時；持股檔每日更新 |

### 2.2 實際覆蓋率（實測，兩組數字都必須看）

**若沿用現行的 `getSectorIndex()`（`limit: 50`）：**

| 項目 | 數值 |
|---|---|
| 母體 | 500 |
| 有版塊歸屬 | 405（81.0%） |
| **無歸屬** | **95（19.0%）** |

**若改用完整持股檔（建議）：**

| 項目 | 數值 |
|---|---|
| 母體 | 500 |
| 有版塊歸屬 | **500（100%）** |
| 無歸屬 | **0** |

> 🔴 **這是本設計最重要的一個實作陷阱，必須先修正才能蓋流程。**
>
> `lib/sector-holdings.js:165` 把持股上限寫成 `Math.min(Number(opts.limit) || 10, 50)`，
> 而 `getSectorIndex()` 固定傳 `limit: 50`。但實測各 ETF 的持股檔內容是：
>
> | ETF | 檔內總數 | 被 50 截掉 |
> |---|---|---|
> | XLI | 83 | 33 |
> | XLK | 76 | 26 |
> | XLF | 76 | 26 |
> | XLV | 60 | 10 |
> | XLY | 47 | 0 |
> | 其餘 6 個 | ≤33 | 0 |
>
> 也就是說：**這 95 檔不是「查不到版塊」，而是「排在第 51 名之後被切掉」。**
> 實測 `CTSH`（XLK 第 54 名）、`AKAM`（XLK 第 52 名）都在檔案裡，
> 只是被 clamp 掉了。
>
> 若不修掉這個上限，階段二會無故丟掉 19% 的母體，而且**表面上看起來像是
> 資料本身的限制**（API 回 `truncated: true`），非常容易被誤判為正常。
>
> 修正方式：把 `getHoldings` 的上限從 50 放寬（例如 200），或讓
> `getSectorIndex()` 傳一個 `limit: Infinity` 的專用參數。
> 成本僅為解析稍微多幾十列，無額外網路請求（同一個 xlsx）。
>
> **已實測驗證可行**：以完整持股檔重跑，原本缺的 95 檔
> **95/95 全部補回，無一遺漏**（含 `AIZ`、`AKAM`、`ALGN`、`AXON`、`BAX`、
> `CDW`、`CFG`、`CTSH`、`DD`、`DOV` 等）。這不是推測，是跑過的結果。

**修正後的實測分佈（母體 500 檔，各版塊成員數，總和恰為 500、無跨版塊重複）：**

| 版塊 | 檔數 | 版塊 | 檔數 |

| XLK 科技 | 76 | XLRE 房地產 | 30 |
| XLF 金融 | 76 | XLB 原物料 | 24 |
| XLV 醫療 | 60 | XLE 能源 | 21 |
| XLY 非必需消費 | 47 | XLC 通訊 | 19 |
| XLP 必需消費 | 33 | | |

取前 N 個優勢版塊後的動態池規模：

| N | 池內檔數 | 相對母體 | 上游請求數（×3） | 90 秒預算 |
|---|---|---|---|---|
| 1 | 約 83 | 17% | 約 249 | 充裕 |
| **2（預設）** | **約 159** | **32%** | **約 477** | **可完整跑完** |
| 3 | 235 | 47% | 705 | 逼近上限，常逾時 |
| 4 | 295 | 59% | 885 | 必然逾時 |
| 5 | 342 | 68% | 1026 | 必然逾時 |

實測 `cross-listed = 0`——每檔 S&P 500 成分股只出現在一個 SPDR ETF 裡。
「主場判定」（取權重最高者）目前不會被觸發，但仍應保留：這是防禦性設計，
一旦未來某檔同時出現在兩個 ETF，沒有這段邏輯就會出現同一檔股票被歸到
兩個版塊、在兩個版塊都入池的重複計算。

### 2.3 納入條件（必須全部滿足）

| # | 條件 | 依據 | 失敗分類 |
|---|---|---|---|
| 1 | 在 500 檔母體中（美股、非中概股） | `pool.enforceUniverse()` | `OUT_OF_UNIVERSE` |
| 2 | 有版塊歸屬 | `getSectorIndex().map.has(sym)` | `SECTOR_UNKNOWN`（**修正上限後應為 0**） |
| 3 | 所屬版塊 ∈ FAVORED 集 | 階段一輸出 | `SECTOR_NOT_FAVORED` |

### 2.4 剔除分類（必須分開統計，不可合併）

```
OUT_OF_UNIVERSE    非美股／中概股           → 規則性排除（固定規則）
SECTOR_UNKNOWN     有股票但查不到版塊歸屬   → 資料不足（不是不合格）
SECTOR_NOT_FAVORED 版塊未入選              → 策略性排除
```

**為什麼一定要分開：** 這三者的除錯方向完全相反。
`SECTOR_UNKNOWN` 暴增代表「持股檔沒抓到或上限截斷」——是**資料管線壞了**；
`SECTOR_NOT_FAVORED` 暴增只是「這次選的版塊少」——是**策略結果**。
若合併成一個「已排除 255 檔」，資料管線壞掉時使用者只會看到一個大數字，
無從發現異常。**修正上限後 `SECTOR_UNKNOWN` 應恆為 0；一旦不為 0 就是告警訊號。**

### 2.5 輸出結構

```
{
  universe: 500,
  withSector: 500,            // 修正上限後
  withoutSector: 0,           // 應為 0；非 0 即代表持股檔異常
  favoredSectors: [ { key, label, rank, strengthScore, quadrant, crossNext, members } ],
  dynamicPool: [ 'AAPL', 'MSFT', … ],   // 前 2 個版塊約 159 檔
  excluded: {
    sectorNotFavored: { count, sample },
    sectorUnknown:    { count, symbols },   // 完整列出，不是抽樣
  }
}
```

**效能紅利（修正後，預設前 2 版塊）**：母體 500 → 約 159 檔，
上游請求從 1500 降到約 477，在 90 秒預算內可以**完整跑完**——
這是原本 500 檔做不到的。若取前 3 版塊（235 檔 / 705 請求）就會逼近上限，
這也是預設定為 2 的直接原因。
換句話說，**版塊前置不只是策略，也是讓全量篩選變得可行的關鍵**。

## 3. 階段三：個股選股

### 3.1 沿用既有參數（不變動）

| 參數 | 預設 | 含義 |
|---|---|---|
| `minScore` | 55 | 技術面綜合分下限（0–100） |
| `maxDistAtr` | 3.0 | 距買區上限，以 **ATR 倍數**正規化（不用百分比，因無區分度） |
| `minPrice` | 1 | 過濾低價噪音股 |
| `maxAtrPct` | 12 | 波動上限；超過此值區間預測本身不可靠 |
| `minAvgVol` | 0 | 20 日均量下限（0 = 不過濾） |
| `limit` | 30 | 回傳筆數 |

### 3.2 個股評分的七個維度（`lib/analyzer.js`）

| key | 標籤 | 衡量 |
|---|---|---|
| `maPosition` | 均線多空排列 | 價格與多條均線的相對位置 |
| `supportDist` | 支撐距離 | 現價距下方支撐 |
| `momentum` | 動能（RSI/MACD） | 短中期動能 |
| `volume` | 量價關係 | 量能是否配合 |
| `trend` | 中期趨勢 | 趨勢方向與強度 |
| `resistanceRoom` | 上行空間 | 現價到上方壓力的空間 |
| `volatility` | 波動風險 | 波動是否可接受 |

`verdict` 分級：`buy`(≥72) ／ `watch-buy`(≥58) ／ `watch`(≥45) ／ `caution`(≥32) ／ `avoid`(<32)

### 3.3 最終優先順序（四鍵排序）

```
第 1 鍵：版塊排名          ASC   （rank 1 的版塊優先）
第 2 鍵：個股技術評分       DESC
第 3 鍵：距買區（ATR 倍數）  ASC   （越接近買區越好；負值＝已進入買區）
第 4 鍵：盈虧比            DESC
```

**為什麼版塊排名放第一鍵（而不是把版塊分數混進個股分數）：**
- 可稽核：使用者看到「第 3 名版塊的 88 分股票排在第一名版塊的 76 分股票之後」，
  能立刻理解原因（版塊優先），而不是面對一個無法解釋的加權數字。
- 可回測：兩段式排序的每一段都能單獨驗證。

**代價必須講出來：** 版塊優先會造成**集中度風險**——
前 10 名可能全部來自同一個版塊。因此同時提供 `sortBy=score`（個股優先）模式，
並在結果中輸出「若改按個股優先，前 10 名會有哪些變動」的對照，
讓使用者自己決定要「順風集中」還是「分散」。

### 3.4 選配訊號：版塊內相對強度（值得加，但非必要）

用同一套 RRG 機制，把基準從 SPY 換成**該股所屬的版塊 ETF**：

```
computeTrack(close_stock, close_sectorETF, period)
```

得到「這檔股票在它自己的版塊裡，是領頭羊還是拖油瓶」。

- `ratio > 100` → 跑贏所屬版塊（版塊內領先）
- 這比「絕對漲跌」更能回答「該版塊轉強時，買哪一檔」

成本：每檔多一次序列取數（可用現有 K 線快取緩解）。
建議列為**可選開關**（預設關閉），因為它會讓階段三的耗時增加約 1/3。

### 6.1.2 第三個缺陷：`e2e-rec-basis` 的同一類漏洞

修完 `e2e-sector-flow` 的 `quote` 之後，順著檢查才發現 `e2e-rec-basis.cjs`
有**完全相同的問題**：只樁 `ds.chart`，沒樁 `ds.quote`。而且它多一層 ——
帳本裡是港股 `2015.HK`，`tracker.run()` 會呼叫
`fx.ratePerUsd('HKD', datasource)`，而 `fx.js` 是透過
`datasource.quote('USDHKD=X')` 取得匯率的。於是：

- **只樁 `chart`** → `quote` 打真網，匯率與報價都從上游來
- **補樁 `quote` 但不認得 `=X`** → 匯率會拿到「股價」當成 7.8 之類的數字，
  折算後的損益**靜默偏離**，測試照樣可能全綠

這裡的教訓比第一個更值得記：**「有樁」不等於「離線」，也不等於「數值正確」**。
要用斷言去確認「這個請求真的被接住了」，不能只確認「我寫了樁」。

同時把該測試的 `networkidle` 改成 `domcontentloaded` + 等待資料列。
原因：這頁會先跑一輪更新、再對每列打 `/api/tracker/chart.png` 取縮圖，
兩者串起來很容易超過 30 秒；`networkidle` 逾時的錯誤訊息只說
「page.goto 逾時」，看起來像整頁壞掉，實際只是等待條件太嚴。

### 6.1.3 第四個缺陷：把「跑測試的日期」當成斷言對象

`tracker-smoke.cjs` 有一條「建倉當天不判出場」，原本的斷言是：

```js
assert.strictEqual(r.status, 'holding');   // 尚未結案
assert.strictEqual(r.exit, null);          // 不得有出場記錄
```

這兩行成立的前提是「上游的日線只到建倉那天」。但真實 K 線每天都會往後長：
那筆 ZS 於 2026-11-25 以 216 建倉，止賺設 217；過了幾天，11-26、11-27 的
日線補上來，止賺被正常觸及、合法結案，狀態變成 `target_hit`。於是測試報錯，
而**程式完全正確**。

這裡的核心錯誤是**斷言了代理指標而不是不變量**：

| | 原本斷言 | 應該斷言 |
|---|---|---|
| 對象 | `status === 'holding'`（當下狀態） | `exit.date > entry.date`（規則本身） |
| 何時失效 | 上游資料一更新就失效 | 只有規則真的被破壞才失效 |
| 測到的是 | 跑測試的日期 | 程式的行為 |

原本那條測試本質上在測「今天上游更新到哪一天」，那不是程式正確性。
已改成「出場日必須嚴格晚於建倉日」——不論是否已出場都成立，
且不隨時間失效。

**變異驗證**：把 `lib/picks-tracker.js` 建倉當天的 `continue` 拿掉後，
新斷言立刻失敗並給出可用訊息：
`出場日 2026-11-25 必須晚於建倉日 2026-11-25——同日即出場表示建倉當天就判了出場`。
可見放寬後並沒有變空斷言。

**同時修正了測試分類**：`tracker-smoke.cjs` 的檔頭自己寫明「用真的上游跑一次」，
它是**連網**測試，卻被放在 `test:offline` 裡。它在離線鏈裡能過，
是因為沙盒把 Yahoo 限流成 429、資料取不到，測試走進 `pending → 略過` 的
逃生門——跟 6.1.2 是同一種病：**「通過」不代表「驗證過」**。
已將其移出 `test:offline`（26 個檔案，全部不碰網路），
`test:all` 仍保留它。建倉當天的規則本身在離線層另有覆蓋
（`picks-tracker-unit.cjs` 與 `picks-tracker-mutation.cjs` 的專屬變異），
所以移出後防護沒有缺口。

### 6.2 本次實作中發現並修掉的既有缺陷

這三項都不是新功能的需求，而是「一接上去就暴露」的既有問題：

1. **`rankSectors()` 丟棄 `cross`** — 它挑欄位重建物件，`cross` 因此消失。
   下游所有 `s.cross` 判斷永遠是 `undefined`，降級規則變成永不觸發的死碼。
   最惡劣的是**完全沒有錯誤訊息**，輸出看起來一切正常，只是「山頂領先者
   不會被降級」。已修，並用單元測試 E1/E2 與變異測試雙向釘住。

2. **`rrg.DEFAULT_PERIOD` 沒有被匯出** — 它是 `undefined`。
   傳進 `computeTrack()` 後 DEMA 迴圈一次都不執行，`ratio` / `momentum`
   全是 `null`，於是每個版塊都被判成「資料不足」，整條流程在階段一就失敗。
   症狀極具誤導性：錯誤訊息說「所有版塊的資料都不足以計算 RRG」，
   看起來像上游行情抓不到，實際上資料完好、是參數是 `undefined`。
   已改用 `rrg.normPeriod(opts.period, timeframe).value`。

3. **`isFinite(null) === true`** — 四鍵排序的空值檢查原本用 `isFinite()`，
   結果 `null` 被轉成 `0`，而 `0` 在「距買區」這一鍵裡是**最理想的值**
   （正好在買區上緣）。缺值的標的因此會被排到最前面。
   已改為先排除 `null` / `undefined` / 空字串。

### 6.3 已知的行為邊界

- **`SECTOR_UNKNOWN` 非 0 就是告警**，不是「這些股票不合格」。前端會把該列標紅。
- **`sortBy=sector` 在沒有版塊資料時會退回 `score`**，並在 `stats.notes` 留下說明。
  靜默假裝成功是最難察覺的失敗，因此這裡選擇明確退回。
- **版塊流程失敗時不降級**成一般篩選。使用者明確要求版塊優先，
  默默回一份沒有版塊依據的清單等於「假成功」。端點回 `200 + ok:false`
  （不是 4xx/5xx，因為那不是請求錯誤），前端走錯誤卡並提供「改用一般篩選」。
